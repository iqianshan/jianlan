## 2. 复现方式

```powershell
# 冒烟（约 2 分钟）：先验证"按键真的落到了被测窗口上"
python tools/ac03/run_ac03.py --hours 0.028 --cycle 8 --sample 20

# 正式 8 小时
python tools/ac03/run_ac03.py --hours 8 --cycle 45 --sample 60
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--exe` | `publish\Jianlan.exe` | 被测产物 |
| `--work` | `D:\ac03` | 工作目录，下分 `app\`（被测副本）与 `sandbox\`（被操作的文件） |
| `--cycle` | 45 s | 每轮随机挑 7 条路径执行 |
| `--sample` | 60 s | 采样间隔 |
| `--seed` | 20261114 | 动作序列可复现 |

隔离设计：被测 exe 连同 `portable.flag` 复制到 `D:\ac03\app\`，设置、收藏、标签、日志全部落在
`app\data\`，不写用户真实的 `%LOCALAPPDATA%`；文件操作只在 `D:\ac03\sandbox\` 内发生。

## 3. 驱动的 20 条路径

进入子目录、返回上级、后退、前进、地址栏跳转、视图切换、搜索当前目录、全选、复制粘贴、
新建文件夹、新建文本文档、重命名、删除到回收站、撤销、属性对话框、复制完整路径、收藏、
新建/切换/关闭标签、双窗格开关、预览窗格开关。

全部走键位（`docs/shortcuts.md`），不依赖像素坐标——换字号或改窗口大小都不会让压测退化成"测鼠标"。
每轮固定补一次 `F5` 刷新，删除类动作后紧跟 `Ctrl+Z`，回收站不累积。

## 4. 判定口径

四项同时成立才算 PASS：

| 检查 | 判据 | 数据来源 |
|---|---|---|
| 崩溃 / 未处理异常 | 计数为 0。退出码非 0 或 WER 有 1000 事件即记崩溃；`crash.log` 只补托管异常，原生 AV 不写它（§6.5） | 进程退出码 + WER 事件日志 |
| 挂死 | 主窗口 `WM_NULL` 1 秒内无响应即终止并留现场 | `SendMessageTimeoutW` |
| 句柄增长 | 末点相对**热身后基线** < 10% | `GetProcessHandleCount` |
| GDI 对象 | 峰值 < 2000 | `GetGuiResources(h, 0)` |

两项附加自检，用于证明"这一轮不是空跑"：

| 自检 | 做法 | 为什么需要 |
|---|---|---|
| `actionsEffective` | 沙箱目录 `mtime` 是否随动作变化 | 按键打在别的窗口上时，8 小时跑完也只有"没崩"，看不出应用是否在干活 |
| `focusResets` | 某段区间内动作在发、沙箱却零写入 → 判为焦点丢失，补 `Esc`+`方向键` 拽回列表 | 模态框、搜索框、拖选都可能把键盘焦点挪走，8 小时里必然遇到 |
| `appSelfExits` | 进程消失时的退出码与 `crash.log` 增量：`exit=0` 且无新增记为自退并重启，其余记崩溃 | 关闭最后一个标签就是关窗口，属正常操作，不能算崩溃（§6.4） |

## 6. 本轮发现

### 6.1 句柄基线不能取"第一个采样点"（口径缺陷，已修）

首轮冒烟末点比首点涨 16.39%，看似泄漏。查采样序列：1324 → 1495 → 1541 → 1535 → 1545 → 1541，
第 1.5 分钟后基本走平。启动阶段的 XAML 资源、图标缓存、字体回退都是按需加载，属于热身，
拿它当基线必然误判。现改为取热身之后的点（8 小时段取第 10 分钟，冒烟段取 1 分钟内的首个点），
基线位置一并写进 `checks.baselineAtMin`。

### 6.2 搜索框按 Esc 退出后，文件列表拿不回键盘焦点（产品缺陷，待修）

`Ctrl+F` → 输入关键字 → `Esc` 之后，`Delete`、`Ctrl+Shift+M`、`F2` 全部失效；
界面看起来已经回到目录列表，实际操作对象还停在搜索框上。

| 收尾动作 | 之后新建文件 | 结论 |
|---|---|---|
| `Esc` 一次 | 120 → 120，失效 | 现状 |
| `Esc` 两次 | 120 → 121，生效 | 需补一次 Esc 才回到列表 |
| `Esc` + 方向键 | 121 → 122，生效 | 用户实际会这么试 |
| `Esc` + `Tab` | 122 → 123，生效 | — |
| `F3` 双窗格 | 125 → 125，失效 | 双窗格不改变焦点归属 |

取证脚本：`tools/ac03/probe_focus.py`。压测脚本里 `act_search` 已补第二下 `Esc`，
但这是绕过，不是修复——真实用户按 `Esc` 关搜索后接着按 `Delete`，删不掉且没有任何提示。
按 §12 的 AC-08（全流程可仅用键盘完成），这属于应当修的口径问题，建议 1.1 修：
搜索框退出时把焦点显式交还给文件列表。

### 6.3 "返回上级"会走出沙箱（脚本缺陷，已修）

`Backspace` 按设计就是回父目录，走出 `sandbox\` 属正常行为；但原脚本只在采样点核对窗口标题，
一轮 7 个动作里有 3–4 个会落在 `D:\ac03` 根上，沙箱计数因此失真。现改为每轮起步先归位。

### 6.4 驱动把应用自己关掉了（脚本缺陷，已修）

第 1 次 8 小时压测跑到 9 分钟，应用消失。现场：`appExitCode=0`、`crash.log` 无新增字节、
应用日志没有异常行——**是正常退出，不是崩溃**。

根因在 `act_tabs`：`Ctrl+T` 开标签 → `Ctrl+Tab` 切标签 → `Ctrl+W` 关标签。只剩一个标签时
`Ctrl+W` 就是"关窗口"；只要有一次 `Ctrl+T` 被吃掉（焦点飘到搜索框、预览窗格或模态框上），
下一步的 `Ctrl+W` 就把最后一个标签关掉，应用干净退出。日志里紧接着的 7 次"抢前台失败"
是事后现象——窗口已经没了。

两条修法一起上：

1. **常驻一个备用标签**。启动时多按一次 `Ctrl+T`，此后每轮"开一个、关一个"净增 0，标签数
   始终 ≥2，单次 `Ctrl+T` 丢失也不会归零。
2. **自退即重启接续**。跑到一半发现进程没了，先看退出码与 `crash.log`：`exit≠0` 或有新行才
   记崩溃并停跑；`exit=0` 且无记录则记 `appSelfExits`（上限 30 次）后重启、重新落位、继续采样。

这条缺陷只在压测脚本里，产品"关掉最后一个标签即关闭窗口"是正常行为，不作为缺陷记录。

### 6.5 第 2 次压测 15.4 分钟崩溃：`0xC0000005` @ `DUI70.dll`（产品/环境待定，阻塞 AC-03）

第 2 次压测 23:37 起跑，23:52:29 停跑。与 §6.4 不同，这次是**真崩溃**：

| 项 | 值 | 来源 |
|---|---|---|
| 崩溃时刻 | 2026-11-14 23:51:46 | WER 事件 1000 |
| 退出码 | `3221225477` = `0xC0000005` | 驱动侧 `proc.poll()` |
| 异常 | 访问违例，`msctfui`/`DUI70` 路径 | WER `Sig[6]` |
| 故障模块 | `DUI70.dll` 10.0.26100.9818，偏移 `0x65642` | WER `Sig[3..7]` |
| `crash.log` 新增 | 0 字节 | 托管异常处理器抓不到原生 AV |
| 停跑前采样 | 11 点，末点 15.4 min | `ac03-20261114-233708.jsonl` |

崩溃前 14 分钟的资源曲线：私有提交 139.6 → 181.2 MB（单调上涨，约 3 MB/min），
句柄 1354 → 1528 后回落到 1495 上下（无泄漏形态），GDI 154 → 198（平稳）。
提交内存这条曲线**单独记录**：8 小时按此斜率会到 1.4 GB，需要下一次长跑确认是缓存还是泄漏。

**定位到函数级**：把故障偏移喂给 `DUI70.dll` 的导出表，它夹在
`DirectUI::Element::_SetNeedsLayout`（`0x65600`）与
`DirectUI::HWNDElementProvider::QueryInterface`（`0x65670`）之间——即崩溃发生在
**DirectUI 元素的布局重算**里，不是文件操作、不是渲染管线。

**进程里的 DirectUI 是谁带进来的**：崩溃报告列出了完整模块表（227 项），其中与应用自身无关的有：

| 来源 | 模块 |
|---|---|
| 搜狗输入法 TSF 文本服务 | `SogouTSF.ime`、`SogouPY.ime`、`systembeautify_bundle64.dll`、`PicFace64.dll`、`ichat_bundle64.dll`、`isgpet_bundle64.dll` |
| 微软 TSF 输入法 UI | `msctfui.dll`、`MSCTF.dll`、`textinputframework.dll` |
| Shell 命名空间 / 文件预览 | `Windows.FileExplorer.Common.dll`、`explorerframe.dll`、`ntshrui.dll`、`CHARTV.dll`、`virtdisk.dll` |
| 第三方 shell 扩展 | `TortoiseSVN.dll`、`TortoiseStub.dll` |

已确认这些模块是"输入法与 shell 命名空间"在进程内加载的结果（`AppInit_DLLs` 为空，
不是注入）：应用只要拥有可获得键盘焦点的文本框，TSF 就会把输入法组件拉进来。
本产品是 WPF，自己不产生任何 DirectUI 元素。

**复现实验（快速桶，全部无崩溃）**：

| 桶 | 动作 | 次数 | 结果 |
|---|---|---|---|
| `type` | 地址栏跳转 / 搜索 / 重命名 / 新建 | 40 | 无崩溃 |
| `props` | 属性对话框开→Esc | 60 | 无崩溃 |
| `tabs` | 开→切→关标签 | 60 | 无崩溃 |
| `panes` | 双窗格 / 预览窗格 | 60 | 无崩溃 |
| `batch18` | 按崩溃那一批的**原顺序**循环（重命名→前进→全选→属性→地址栏→搜索→重命名） | 140 | 无崩溃 |

脚本：`tools/ac03/repro_crash.py --mode <桶> --iters <次>`。
结论：没有"某一条动作必定崩"的确定性路径，只有原节奏（每 45 秒 7 个动作、中间大量空闲）
跑了 15 分钟才撞上——典型的**时序相关**，不是功能分支错误。

**当前结论**：崩溃落在 DirectUI 布局，而本产品代码不产生 DirectUI 元素；进程内的
DirectUI 来自搜狗输入法与 shell 组件。但在拿到调用栈之前，不能判定是"第三方组件自身缺陷"
还是"我们的模态框 + 连续打字时序把某一方带进了非法状态"。因此 AC-03 **判不通过**，
不做"环境原因"的免责处理。

**已就位的取证条件**（下次崩溃即可定案）：

| 项 | 内容 |
|---|---|
| 本地转储 | `HKCU\...\Windows Error Reporting\LocalDumps\Jianlan.exe`，`DumpFolder=D:\ac03\dumps`、`DumpType=2`（完整） |
| 栈提取 | `python tools/ac03/scan_dump.py D:\ac03\dumps\<文件>.dmp`，不依赖 windbg/dotnet-dump |
| 输入法对照 | `run_ac03.py --input 00000409` 把被测窗口的输入语言钉到 en-US，与中文输入法各跑一轮 |

**判定口径修正**：`crash.log` 只能捕获托管异常，原生 AV 一个字节都不会写。
AC-03 的"0 崩溃"从此以**进程退出码 + WER 事件 1000/1002**为准，`crash.log` 只作辅助。

### 6.6 复跑 15.4 分钟同点复现，`crash.log` 首次留下托管异常（已修，待验证）

第 3 次 00:01:56 起跑，计划 42 分钟，实际 00:17:19 停跑——`elapsedMin` 15.4、退出码
`3221225477`，与 §6.5 **同一分钟、同一动作数（127）、同一批次**（`--seed 20261114` 固定序列）。
这次 `crash.log` 写了 1176 字节，是上一轮缺的那半块证据：

```
System.InvalidOperationException: PaneView 尚未附加视图模型：宿主必须先调用 Attach.
   at Jianlan.App.Views.PaneView.ResolveFolderIconsAsync(Int32 generation)  PaneView.Icons.cs:line 32
   at System.Threading.Tasks.Task.<>c.<ThrowAsync>b__128_0
```

**根因链**：`ResolveFolderIconsAsync` 是 `async void`，由 `Dispatcher.InvokeAsync`
排在 `ApplicationIdle` 上；同一时段里"关分屏"调 `Release()` 把视图模型置空，回调晚到，
`Vm` 的非空访问器抛异常。`async void` 没有调用方可接，异常只能落 `DispatcherUnhandledException`。
两次事件相距约 1 分钟：先托管异常，随后同址 `DUI70+0x65642` 原生 AV——与 §6.5 的
"DirectUI 布局重算"对得上：图标解析改了线程模型，把 Shell 的 DirectUI 拖进了并发访问。

**四处改动**：

| 改动 | 文件 | 理由 |
|---|---|---|
| 视图模型改模式匹配 `ViewModel is not { } vm`，取快照包 try/catch | `Views/PaneView.Icons.cs` | 宿主换绑或收走窗格时静默退出，图标是视觉细节，不能带走进程 |
| 图标解析由 `Task.Run` 迁到常驻单线程 STA（带消息泵） | `Shell/ShellWorker.cs`（新增） | DirectUI 只能在创建它的线程上布局，且需要消息泵；原路径是线程池 MTA，与 UI 线程 STA、缩略图各条 STA 并发摸同一份 Shell 状态，套间还不一致 |
| 删掉 `ShellIconProvider.EnsureComInitialized()` 及其 P/Invoke | `Shell/ShellIconProvider.cs`、`Services/FolderIcons.cs` | STA 线程的 COM 由运行时初始化，手写 `CoInitializeEx` 既多余又会与套间模型打架 |
| 崩溃日志版本号从硬编码 `0.1.0` 改读 `AppInfo` | `Diagnostics/CrashLogger.cs` | 现场报告写错版本，事后核对产物会误判 |

`dotnet build -c Release` 通过。缩略图那条"每次请求一条 STA 线程"暂未并入 `ShellWorker`
（它有超时护栏，合并要先解决超时与线程泄漏的冲突），所以本次只收敛图标这一路。

**仍未闭环**：崩溃时点是否消失，要看修复版重跑。en-US 输入语言对照实验 00:18:46 起跑，
跑到 11.3 分钟（8 个采样点，提交 131.9 → 161.0 MB）被中止，**没跨过 15.4 分钟这个坎**，
因此"是否与搜狗输入法相关"仍无结论。

**验证门槛**（下一轮必须满足，才算这次修复有效）：

1. 重打产物后先跑 2 分钟冒烟，`actionsEffective=true`；
2. 至少跑到原崩溃点 2 倍（30 分钟）不崩，再谈 8 小时；
3. 8 小时段仍需满足 §4 四项，另加"私有提交斜率"——§6.5 记录的 3 MB/min 若在长跑中不收敛，
   单列内存问题处理。

### 6.7 同产物两轮未复现，但不足以判定修复（2026-11-15 白天）

### 6.14 结构性改造：模态窗常驻复用（第 12 轮起）

前三次修复都在"销毁前多做一步"上打补丁，方向不对：崩溃链的入口是 TSF 为**每个拿到焦点的
HWND** 建立默认文本存储与对应 DirectUI 元素，而我们的模态窗每次都是新 HWND、关即销毁。
压测 69 分钟里这种建/毁发生上百次，输入法把界面元素挂在那份上下文上，HWND 没了绑定还在，
下一次按键（`CtfImeToAsciiEx`）就写到了已摘除的节点——即 `dui70+0x65642` 的 `mov [rdx], rax`，`rdx = 0`。

改法：模态窗建一次、之后只 `Hide`/`Show`，HWND 活到进程结束，链路上不再有反复的建/毁。

| 文件 | 改动 |
|---|---|
| `Views/ModalSession.cs` | **新增**。手动模态：禁父窗 → `Show()` → `Dispatcher.PushFrame` → `Hide()`，并恢复原焦点 |
| `Views/ConfirmWindow.xaml.cs` | 单例复用；`Ask`/`Notify` 走 `ModalSession`；`DialogResult` 换成内部 `_finish` 回调；Esc/Enter 自行接管 |
| `Views/TextPromptWindow.xaml.cs` | 同上；抢焦点与选中初值从 `Loaded` 挪到每次显示后（复用后 `Loaded` 只触发一次） |
| `Shell/ImeFocusRelease.cs` | 拆出 `CancelComposition`（隐藏前只撤组字、**保留** IMM 关联），解除关联挪到真正的销毁路径 |

不改的：窗口 XAML、调用方的同步语义（`Ask` 仍然阻塞到用户作答）、模态外的任何行为。

顺带修掉的一个老问题：`ShowDialog` 关闭时由 WPF 把焦点还给父窗，手动模态要自己还，
而且要还到"弹出之前那个元素"上——原来落在窗口壳上，后续按键全部打空，
正是 §6.13 里 15% 批次"本段没有写入"的来源。

**代价与风险**：模态语义从框架改为自维护，需要覆盖 Esc/Enter/Alt+F4/父窗禁用/焦点归还五条路径；
应用退出时必须放行真实关闭（`Application.MainWindow` 已不可见时不再拦截 `Closing`），
否则进程退不出去。这五条路径由压测的 20 条动作反复触发，回归面是够的。

**验证门槛（不变）**：连续两轮 21 分钟 PASS + 8 小时 0 崩溃 + GDI 不逼近 2000。
另加一条：`focusResets` 应显著低于每百批 15 次。

### 6.15 驱动把"瞬时卡顿"判成"应用自退"（脚本缺陷，已修）

改完模态窗后第一轮冒烟（10:28 起跑，`--cycle 4` 快节奏）在 2.3 分钟处报
"应用自退（exit=0，无崩溃记录），第 1 次重启"，随后"重启失败，停跑"。现场三份证据互相矛盾：

| 来源 | 说法 |
|---|---|
| 驱动日志 | 应用自退 exit=0 |
| `singleinstance.log` | 10:30:33 第二个进程"Mutex 已被占用，判定为非主实例"——**第一个进程还活着** |
| 手工 `SendMessageTimeout(WM_NULL)` | 0.7 ms 有回音，且就是前台窗口 |

根因在驱动的死判定：

```python
dead = not responsive(hwnd)          # SendMessageTimeout(WM_NULL, 超时 1000ms)
if dead:
    code = proc.poll()               # → None（进程还在！）
    if code not in (0, None) or ...  # None 不进崩溃分支
    # 落到"自退"分支，且日志里把 code 写死成 exit=0
```

`responsive()` 只等 1 秒，而复制整个目录、Shell 回收站操作、缩略图首屏都会把消息泵
堵上一两秒；这一轮 `--cycle 4` 让动作密度翻倍，撞上了。**把 `proc.poll() is None`
当成了"自退"**，还去启动第二个实例，被单实例守卫挡回来，于是"重启失败"。

修法：`dead` 且 `poll()` 仍是 `None` 时，复查两次（各等 1 秒），仍不响应就记为
`unresponsive` 继续跑，**不再当作自退**；自退分支要求 `code == 0` 才进；`s is None`
且进程还在时跳过该采样点。这条不修，8 小时长跑随时会被自己人判死。

### 6.17 真正的触发面：`SHFileOperation` 的 Shell 进度界面（2026-11-16 上午，本轮定案）

模态窗复用（§6.14）上线后连跑三轮，全崩，且都崩在同一帧。三轮还各留了一份转储
（10:30:29 / 10:54:40 / 11:15:39），把现场补全了：

| 轮次 | 时长 | 转储 | 与上一点的间隔 |
|---|---|---|---|
| 冒烟（`--cycle 4`） | 2.3 min | `261116_103025` | — |
| 21 分钟（第 1 次） | 18.6 min | `261116_105437` | 1.9 min |
| 21 分钟（第 2 次） | 17.3 min | `261116_111534` | 0.3 min |

**先纠一个误判**：这三次里有两次被记成"驱动卡死"、一次被记成"应用自退"。实际都是崩溃——
`procdump -e` 靠 `DebugActiveProcess` 抓转储，附着瞬间会把被测进程**整体挂起**几十秒。
这期间 `poll()` 仍是 `None`、`WM_NULL` 当然没有回音，于是驱动既判"自退"又判"无响应"，
还会去启动第二个实例（被单实例守卫挡回，于是"重启失败"）。判据改成"转储目录里多了一份
`.dmp`"，比退出码更早、更可信（§6.18）。

**崩溃线程不是 UI 线程。** 11:15 那份转储的崩溃线程是 `23108`，而 UI 线程（CPU 25.2 秒那条）
完全没被卷入。结合三处现场：

1. `--probe-windows` 在 17.2 分钟抓到窗口 `#32770`，标题是**"这将取消所有正在进行的传输。"**
   ——这是 Shell 传输界面的对话框，不是我们的 WPF 窗口；
2. 同一采样点 GDI 从 **196 跳到 641**（提交内存 170 MB → 338 MB）——一扇 Shell 进度界面
   就位时的典型开销；
3. 栈上自内向外恒为 `dui70 → duser → msctf → shell32 → textinputframework`。

对照代码：`FileOperations.DeleteAsync` 为每次删除单开一条线程（`Jianlan.Delete`，STA），
在**没有消息泵**的线程上直接调 `SHFileOperationW`，而 `fFlags` 只给了
`FOF_NOCONFIRMATION | FOF_NOERRORUI | FOF_ALLOWUNDO`——**没有 `FOF_SILENT`**。
Shell 于是按"要显示进度"来准备：在本进程里建一扇 DirectUI 进度窗，靠窗口消息推进状态。
这条线程不泵消息，TSF 又给新窗口挂上输入上下文，两条线在窗口建/毁时互踩，
落到 `dui70+0x65642` 的 `mov [rdx], rax`（`rdx = 0`：摘除链表时前驱为空）。

为什么崩点漂移（15.4 / 69 / 18.6 / 17.3 分钟）：进度界面只在删除量足够大、耗时足够长时才出现。
`act_select_all`（`Ctrl+A`）之后 `act_delete` 会一次删上百个文件，正好够触发；
删一两个文件则一闪而过。这解释了"同一份二进制，有时 21 分钟安然无事、有时 17 分钟就崩"。

**修法**：`fFlags` 加 `FOF_SILENT`（`0x0004`）。不再要 Shell 的进度窗，也就不再有
第二扇 DirectUI 窗口、不需要消息泵、不给 TSF 添新的附着点。代价是批量删除没有进度条——
删除本身是瞬时操作，界面已有"正在删除"状态，不需要 Shell 那扇窗。

**同时更正 §6.14 的结论**：模态窗常驻复用**没有**修掉这个崩溃，它只是把窗口建/毁的
次数降下来（顺带修掉了 15% 批次零写入的焦点问题，以及必须显式声明 `ShutdownMode`）。
根因在文件操作这条线，不在模态窗。保留复用是因为它本身站得住，但不能拿它当崩点已修的证据。

```

   at ModalSession.Run(...)  ← 第 85 行 window.Show()
   at ConfirmWindow.Notify(...)
   at PaneView.ShowProperties()
```

首条 12:11:09（第 28 分钟），末条 19:39:35，平均间隔 2.3 分钟，与"每批动作里有 1/3 概率
碰到属性/确认"的频次吻合——即**从第 20 分钟起，每一次弹窗调用都抛，一次都没成功**。
窗口快照可以佐证：确认窗（标题 `Delete`）在 3.3 / 8.2 / 18.6 / 20.2 分钟各出现一次，
**20.2 分钟之后再没出现过**，此后只有空标题的提示气泡。

**机制（已用 `tools/ac03/probe_singleton.py` 复现）**：`ModalSession` 只在"某一轮模态进行中"
订阅 `Closing`，一轮结束就在 `finally` 里摘掉。于是窗口隐藏期间**没有任何守卫**——
此时收到 `WM_CLOSE`，WPF 直接销毁 HWND。之后再 `Show()` 必抛，而单例 `_instance` 又不会重建，
整条链路永久哑掉。探针实测：隐藏窗收到 `WM_CLOSE` 后 `IsWindow` 由 True 变 False，
第二次属性**不弹窗**，`crash.log` 新增 4633 字节。

至于 WM_CLOSE 从哪来：驱动 `dismiss_strays` 的最后一步是 `PostMessage(WM_CLOSE)`，
前置判据是 `IsWindowVisible`。`Esc` 走 `SendInput`，是异步投递；图标首屏或目录复制把
消息泵堵住时，300 毫秒内 Esc 还没被处理，窗口仍是可见的，于是 WM_CLOSE 被投出去——
Esc 先到（`Finish(false)` → 隐藏 → 摘守卫）、WM_CLOSE 后到（无人拦 → 真销毁）。
这是一条**竞态**，所以只在 8 小时里命中过一次，而不是每次都命中。

这是 1.0 必须修的缺陷，与压测无关：任何外部 `WM_CLOSE`（任务栏关闭、第三方程序、
系统关机流程）都能把常驻窗打掉，而失败是**静默**的——异常被 `CrashLogger` 吞掉，
用户看到的是"点了属性没反应"，重启才好。
