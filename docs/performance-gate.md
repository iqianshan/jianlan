# 启动性能门禁

> 对应 NF-01 / NF-08。本文件是"启动够不够快"的唯一判定依据，任何与之冲突的口头结论均无效。

## 1. 指标定义

启动包含四个不同的时间点，不能用同一个数字混称。**前三个是应用内埋点，起点是 `App`
构造函数，不含进程创建与 CLR / 运行时加载**；第四个是外部计时。

| 指标 | 定义 | 来源 | 当前实测 |
|---|---|---|---|
| **T-render** | `App` 构造 → 首帧绘制完成 | 埋点 `render` | ~380 ms |
| **T-interactive** | `App` 构造 → 窗口可响应输入（Loaded 完成） | 埋点 `loaded` | ~569 ms |
| **T-content** | `App` 构造 → 文件列表首次填充 | 埋点 `firstcontent` | ~600 ms |
| **T-external** | `Process.Start` → 主窗口句柄出现 | 脚本外部计时 | ~769 ms |

**门禁采用 T-interactive。** 理由：窗口画出来了但点了没反应，用户判定为"卡"，不能算启动完成。
T-render 只用于定位问题，不作为验收依据。

**对外承诺采用 T-external。** 这是用户按下图标到看见窗口的真实等待。两者相差约 200 ms，
来自进程创建、CLR 与运行时初始化，以及脚本 10 ms 轮询粒度（约 20 ms）。

两个口径分工不同，都要保留：

- **T-external** 对用户诚实，但受进程创建抖动影响，不适合做回归判定；
- **T-interactive** 对代码改动敏感、噪声小，适合做门禁。若只留 T-external 做门禁，
  一次系统更新带来的进程启动变慢就会被误判成代码回归。

## 2. 阈值

| 口径 | 版本 | P50 | P95 | 判定 |
|---|---|---|---|---|
| 埋点（门禁） | 目标 | ≤ 700 ms | ≤ 900 ms | 通过 |
| | 警戒 | 700–800 ms | — | 通过但必须提交优化说明 |
| | 阻塞 | > 800 ms | — | 禁止合并 |
| 外部（对外） | 目标 | ≤ 900 ms | ≤ 1 100 ms | 写入 README 与发布说明 |

> 原目标为 400 ms，M0 实测后调整为 700 ms。依据见 §5。

## 3. 埋点实现

`src/Lingpane.Core/Diagnostics/StartupTrace.cs`。各阶段含义：

| 标记 | 位置 | 已包含 |
|---|---|---|
| `begin` | `App` 构造函数 | CLR 启动、程序集加载之后的进程内起点 |
| `resources` | `OnStartup` 开头 | App.xaml 资源字典合并（DesignTokens / 主题 / 样式） |
| `fontscale` | `FontScaleService.Apply` 之后 | 字号与字体度量下发 |
| `window` | `new MainWindow()` 之后 | 窗口构造（模板、样式系统首次初始化） |
| `render` | `CompositionTarget.Rendering` 首次回调 | 首次排版与绘制 |
| `loaded` | `Loaded` 事件 | 激活流程（含 IME 上下文） |
| `show` | `Show()` 返回 | — |
| `firstcontent` | 首次目录枚举完成 | 磁盘枚举 + 列表绑定 |

日志落盘位置：`%LOCALAPPDATA%\Lingpane\logs\startup.log`，一行一次启动。

**约束**：`Mark` 路径上不得有磁盘 IO。`Flush` 只在首帧之后调用一次。

## 4. 测量方法

```powershell
dotnet publish src/Lingpane.App -c Release -r win-x64 --self-contained false -o publish
pwsh tools/startup-bench/Measure-Startup.ps1 -Exe publish/Lingpane.exe -Runs 20
```

脚本采集两个值：

- **outer**：`Process.Start` → 主窗口句柄出现。受 10 ms 轮询粒度影响，仅参考。
- **inner**：`startup.log` 的 `total`。这是门禁依据。

注意事项：

1. **必须用 Release + ReadyToRun 测**。Debug 无优化，数字无意义。
2. 脚本不清系统文件缓存，测的是"已运行过"的稳定值。首次冷盘单独记录，不参与判定。
3. 测量期间不要跑其他重负载程序。P95 对系统负载极敏感。

### 4.1 测量有效性前置条件（脚本强制）

WPF 的启动成本主要是 CLR 与框架程序集加载。内存紧张时这些页被 Memory Compression
压缩或换出，每次启动都要解压或调页，耗时可以从 578 ms 涨到 800 ms 以上——
**这段差异与代码无关，但会误判为性能回归**。

因此脚本在执行前先校验环境。**不达标不中止测量**——照常跑完并输出数字，只把结论
降级为"参考数据"、不作出门禁判定（退出码 5）。这样既不会因为机器忙就完全拿不到数据，
也不会让脏数据污染基线。

环境判定分三档，不是简单的合格/不合格：

| 档位 | 条件 | 行为 | 退出码 |
|---|---|---|---|
| 正常 | 可用内存 ≥ 50%，CPU ≤ 60%，离散度 ≤ 1.5 | 正常判定 | 0 / 2 / 3 |
| 偏低 | 可用内存 30–50% | **仍正常判定**，提示"结果可能偏高 50–100 ms" | 同上 |
| 降级 | 可用内存 < 30% 或 CPU > 60% 或离散度 > 1.5 | 出数据但不判定 | 5 |

三个参数：`-MinFreeRatio`（默认 0.5，正常线）、`-WarnFreeRatio`（默认 0.3，降级线）、
`-MaxCpuLoad`（默认 60）、`-MaxSpread`（默认 1.5，离散度）。

**为什么内存分两档而不是一个阈值。** 最初设"< 35% 不测"，实测发现开发机（16 GB，
常驻 WPS、搜狗、ToDesk、企业微信）可用内存长期在 45–55% 波动，门槛过高会导致永远测不了。
但也不能不设——实测 26% 时同一份代码从 578 ms 涨到 789 ms。所以拆成两条线：

- **30% 以下**系统已在压缩工作集，WPF 框架页被反复换出，数据反映的是内存管理策略，不可用；
- **30–50%** 是这类机器的常态，实测对比：51% 时 P50 569 ms、48% 时 556 ms，差异在噪声内，
  不影响趋势判断，只需提示。

**为什么加离散度判据。** CPU 和内存都是采样瞬间的快照，抓不住测量期间的负载变化。
离散度（max/min）直接看数据本身是否稳定，更可靠：

| CPU | P50 | 离散度 | 判读 |
|---|---|---|---|
| 29% | 511 ms | 1.10 | 稳定 |
| 39% | 569 ms | 1.27 | 稳定 |
| 54% | 556 ms | 1.18 | 稳定 |
| 67% | 1 039 ms | 1.69 | **不稳定，降级** |

CPU 上限取 60 而非 50：Windows 空闲机器也常在 30–50% 波动，50 会造成大量误降级；
而 60% 以上启动耗时已明显被调度延迟主导。

退出码约定：

| 码 | 含义 |
|---|---|
| 0 | 通过 |
| 2 | 未通过（代码或基线变化） |
| 3 | P50 通过、P95 抖动超标 |
| 4 | 未采集到埋点（GUI 环境不支持） |
| 5 | **环境未达标，本次为参考数据，不作出门禁判定** |

需要让不达标的数据也照常判定时，加 `-IgnoreEnvironment`。该参数只用于本地临时排查，
**不得用于发布前的正式测量**。

## 5. 基线数据（2026-11-03）

同机对照，Release + R2R，各 3–5 次：

| 方案 | 到 Loaded | 说明 |
|---|---|---|
| WinForms 最小空窗口 | 214–330 ms | 同环境下限参考 |
| WPF 最小空窗口（默认） | 1030–1120 ms | **框架基线** |
| WPF 最小空窗口（禁 IME） | 541–665 ms | 差异来自输入法上下文 |
| WPF HwndSource 直建（绕过 Application/Window） | 978–1051 ms | 证明慢在渲染管线初始化，不在窗口类本身 |
| **Lingpane M0（禁 IME）** | **574–649 ms（20 次：P50 578 / P95 639，min 542 / max 727）** | 业务代码增量约 0–60 ms |

结论：

1. **1.1 秒是 WPF 在本机的框架基线**，不是业务代码写坏了。
2. 单项最大成本是 **中文输入法上下文创建（约 500 ms）**，且同时吃掉约 43 MB 工作集。
3. 绕开 `Application` / `Window` 类没有收益，慢的是首次渲染管线初始化。
4. 业务代码自身开销很小（资源字典 100–150 ms 是唯一可压缩项）。

**同日 15:20 的复测教训（重要）：** 连续跑完 5 轮 10000 项测量后，系统可用内存降到
3.8 / 14.8 GB（26%）、CPU 70%，同一份代码实测 P50 变为 789 ms，P95 达 1601 ms。
用 `git worktree` 检出初始 commit 的版本在同批次测得 P50 1028 ms——
**两者同样变慢，证明差异来自环境而非代码**。

结论：跨时段的启动耗时数字不可比。这也是 §4.1 环境校验的由来。

**同日三轮复测（环境校验阈值调整后）：**

| 轮次 | 环境 | 次数 | 埋点 P50 | 埋点 P95 | 区间 | 外部 P50 | 结论 |
|---|---|---|---|---|---|---|---|
| 1 | 51% / CPU 39% | 20 | 569 ms | 619 ms | 530–671 | 769 ms | 通过 |
| 2 | 51% / CPU 29% | 10 | **511 ms** | 540 ms | 491–540 | 694 ms | 通过 |
| 3 | **48%** / CPU 54% | 20 | 556 ms | 588 ms | 531–628 | 751 ms | 通过 |

基线 578 / 639 ms，阈值（×1.2）694 / 767 ms。三轮均通过。

三轮结果落在 **511–569 ms**，与基线偏差在 −12% ~ −2% 之间。第 3 轮的内存只有 48%
（低于 50% 正常线），P50 仍是 556 ms——说明在 45–55% 这个区间，内存对启动的影响
落在噪声内，不必为此拒绝判定。这与第 1 轮（51%，569 ms）几乎相同，是有力证据。

**轮次间差 58 ms，差异来自 CPU 背景负载（29% vs 39% vs 54%），不是代码。** 因此：

- 单次测量不足以判定回归，至少 10 次取 P50；
- 判定用相对基线的容差区间，而不是"必须等于 578 ms"；
- 对外表述用区间（510–570 ms 埋点 / 690–770 ms 外部），不用单点数字。

**注意内外口径差约 190 ms。** 埋点测的是 `App` 构造 → Loaded；外部计时测的是
`Process.Start` → 主窗口句柄出现，含进程创建、CLR 加载与脚本 10 ms 轮询粒度（约 20 ms）。
对外沟通（README、release note）**必须用外部口径**——那才是用户按下图标到看见窗口的
实际等待；埋点口径只用于定位优化点与门禁比对。

> 同一日下午还出现过一次**整机 WPF 全面变慢**（Lingpane 1102 ms、空窗口 1095 ms），
> 与代码无关，约 20 分钟后自行恢复。诊断方法见 §11——这是本项目最容易误判为
> "代码回归"的情况。

### 6.1 `Show()` 段的两态：启动耗时最大的不确定性来源

2026-11-05 实测发现，同一份可执行文件在两个时间点测出的启动耗时可差 **400 ms 以上**，
差值几乎全部落在 `window` → `srcinit` 这一段（即 `Window.Show()` 内部的窗口源初始化）：

| 状态 | `window` | `srcinit` | 该段耗时 | 总 P50 |
|---|---|---|---|---|
| 快 | 336 ms | 494 ms | 158 ms | 566 ms |
| 慢 | 379 ms | 985 ms | **606 ms** | 1048 ms |

判定依据：`MarkCpu` 记录的进程 CPU 时间在慢态下从 531 ms 涨到 1460 ms（墙钟 606 ms），
即 **1.4 个核在满载计算**，不是在等 IO 或等待消息。

已排除的原因（均为单变量对照实验）：

| 假设 | 实验 | 结果 |
|---|---|---|
| 自定义字体（Alibaba PuHuiTi 2.0）渲染 | 把 `fontFamily` 置空 | 该段仍 560 ms，无关 |
| 输入法上下文创建 | 注释掉 `SetIsInputMethodEnabled` | 该段仍 540 ms，无关 |
| GPU / D3D 设备初始化 | `ProcessRenderMode = SoftwareOnly` | 该段仍 570 ms，无关 |
| 窗口句柄重建 | 记录 `WindowInteropHelper.Handle` | 前后句柄一致，未重建 |
| `TieredPGO` | 关掉后交替对照 | 0 ms 差异，已回滚 |

剩下的是 `HwndSource` / `PresentationSource` 的初始化本身（`activated` 触发时
`PresentationSource.FromVisual` 仍为 null，说明此时窗口源尚未就绪）。
这一段由 WPF 与系统共同完成，代码侧没有可控的介入点。

**测量规则**：判定"某次改动是否引入启动回归"前，先看 `srcinit - window` 是否显著大于 160 ms。
若是，本次数据不可用于代码判定——它反映的是系统状态，不是代码。

> 已知本机存在全局钩子类软件时该段会明显变长（输入法、屏幕录制、安全软件都会插入
> `CreateWindowEx` 的钩子链）。换一台干净的机器对照是最快的验证方式。

| 候选 | 预估收益 | 风险 |
|---|---|---|

已否决：

| 候选 | 结论 |
|---|---|
| `TieredPGO=false` | 交替对照 0 ms 差异，不值得牺牲稳态性能 |

**任何优化若不能通过一次 20 次测量的 P50/P95 对比，不予采纳。**

## 8. 门禁：双层阈值

共享 runner 的绝对耗时不可信，人工检查又不足以防渐进退化。因此门禁分两层，
**两层都用 `baseline.json` 做相对比较，不做绝对耗时断言**。

### 8.1 基准文件

仓库根目录 `baseline.json`，记录"当前认定的正常水平"：

```json
{
  "schemaVersion": 1,
  "capturedAt": "2026-11-03",
  "machine": "Ryzen 7 PRO 5850U / 32GB / Win11 26100",
  "metric": "inner-loaded-ms",
  "runs": 20,
  "p50": 578,
  "p95": 639,
  "ciToleranceFactor": 2.5,
  "localToleranceFactor": 1.2
}
```

`metric` 取值 `inner-loaded-ms`，即 `startup.log` 中进程内 `loaded` 的耗时。
**不含进程创建开销**，因此对 runner 机型差异的敏感度低于外部计时。

### 8.2 CI：拦灾难性退化

`perf-gate` job 在每次 PR 执行：

1. 跑 3 次，取中位数
2. 与 `baseline.p50 × ciToleranceFactor（2.5）` 比较
3. 超出即 job 失败

宽松阈值是刻意的：CI 只负责拦住"引入同步 IO、加载大资源、加了启动期初始化"
这类数量级退化（600ms → 2000ms）。**渐进式退化（每次 +5%）由本地门禁负责。**

两种不判定情形都输出 warning 并跳过，不阻塞合并——**它们不是回归**：

| 情形 | 退出码 | 处理 |
|---|---|---|
| runner 不支持 GUI 渲染，未生成埋点 | 4 | warning + 跳过 |
| runner 环境未达标（内存 <30%、CPU >60%、离散度 >1.5） | 5 | warning + 跳过 |

### 8.3 本地：拦渐进退化

发布前由负责人执行：

```powershell
pwsh tools/startup-bench/Measure-Startup.ps1 -Exe publish/Lingpane.exe -Runs 20 `
     -BaselinePath baseline.json
```

判定规则：`P50 ≤ baseline.p50 × localToleranceFactor（1.2）` 即 694 ms 以内通过。
超出时必须给出原因并更新 baseline，**不允许直接改阈值绕过**。

### 8.4 更新基准的规则

- 只有在**功能合并、性能确认可接受**之后才更新 `baseline.json`
- 每次更新必须同时改 `capturedAt` 与 `p50/p95`，并在 commit message 写明变化原因
- 阈值因子（2.5 / 1.2）非经 ADR 不得调整

这条规则的目的不是"卡人"，而是防止出现"没人知道现在多慢"的状态。

## 9. 列表性能与内存（NF-03 / NF-04 / NF-05）

启动快只解决"第一印象"，大目录卡顿才是每天都会遇到的问题。本节是 M0.5 的实测结论。

### 9.1 测量方法

```powershell
# 1. 生成 10000 项测试目录（约 20 秒）
pwsh tools/perf-fixture/New-TestDirectory.ps1 -Path D:\perf-10k -Count 10000 -Force

# 2. 测量（5 次取中位，带空窗口归一化）
pwsh tools/perf-fixture/Measure-List.ps1 -Exe publish/Lingpane.exe -Path D:\perf-10k -Runs 5 -Normalize
```

`-Normalize` 会在每轮测量前先跑一次 `tools/env-check/WpfBaseline`（纯空窗口），
用"Lingpane 减去空窗口"的增量判定。归一化只能消除同一状态内的漂移，
**跨状态无效**——先确认 GDI 对象在 80 以下（见 9.6），否则数字作废。

实现方式：应用带 `--perf-probe <目录>` 参数启动后，加载目标目录、等待首屏、
逐帧驱动滚动并采样 `CompositionTarget.Rendering` 的帧间隔，最后写出 JSON 并退出。
测的是真实 UI 路径，不是模拟环境。

滚动步长为**每帧 3 行**（按项实际高度计算），模拟滚轮或拖动内容。
不使用"拖动滚动条跳转"——那会在一帧内把数百项拉进视口，测到的是极端场景，
不能代表日常滚动的帧率。

### 9.2 实测数据（2026-11-03，5 次中位，Release + R2R）

| 场景 | 条目 | 枚举 | 首屏 | 帧率 | P95 帧 | 私有提交 | 工作集 |
|---|---|---|---|---|---|---|---|
| 空目录 | 0 | — | 99 ms | — | — | 93.0 MB | 134.5 MB |
| 100 项 | 100 | — | 236 ms | — | — | 99.9 MB | 143.6 MB |
| 10000 项（只加载） | 10000 | 64 ms | 218 ms | — | — | 102.6 MB | 141.8 MB |
| **10000 项（滚动 240 帧）** | **10000** | **66 ms** | **233 ms** | **125.8 fps** | **15.7 ms** | **114.6 MB** | 166.6 MB |

判定：

| 指标 | 实测 | 阈值 | 结论 |
|---|---|---|---|
| NF-03 首屏 | 233 ms | ≤ 800 ms | ✅ 余量 3.4 倍 |
| NF-04 帧率 | 125.8 fps | ≥ 55 fps | ✅ 余量 2.3 倍 |
| NF-05 私有提交 | 114.6 MB | ≤ 120 MB | ✅ 余量仅 5.4 MB |
| 句柄 | 951 | < 10% 增长 | ✅ 滚动前后无增长（951 → 951） |
| GDI 对象 | 56 | < 2000 | ✅ |

> **上表阈值已被 ADR-0002 取代**（2026-11-03）：NF-05 上调为 150 / 185 / 230 MB，
> 并新增相对增量门禁 NF-05R ≤ 45 MB。本节数据保留为优化前的历史记录。

### 9.2.1 降低基础占用的复测（2026-11-03 下午）

余量只有 5.4 MB，M1 无法开工。选定的方案是**降低占用**而非放宽阈值。
先要弄清 93 MB 里哪些是自己的：用 `tools/env-check/WpfBaseline`（纯空窗口）作对照，
测得框架底 **81.0 MB**。也就是说空目录 93.0 MB 里，WPF 框架占 81.0 MB，
本项目自己的代码、资源字典、窗口结构合计只有 **12.0 MB**。

由此确定优化只可能在两处：那 12.0 MB，以及万项目录多出的数据层。

已落实的改动（`FileEntry` / `DirectoryEnumerator`）：

| 项 | 改动前 | 改动后 |
|---|---|---|
| 完整路径 | 每个条目各存一份完整路径，一万条各含重复的父目录前缀 | 只存所在目录（**所有条目共享同一字符串实例**），`FullPath` 首次访问时拼接并缓存 |
| 图标键 | 每条目各分配一个扩展名字符串 | 相同扩展名走驻留表，共用实例 |
| 大小/日期文本 | 构造时全部格式化，一万条 = 两万个字符串 | 首次绑定才格式化，未滚到的条目不产生字符串 |

同一次会话内的对比（空窗口 81 MB 的低态下，各 3 次）：

| 版本 | 万项目录私有提交 | 相对空窗口增量 |
|---|---|---|
| 优化前 | 118.8 MB | +37.5 MB |
| 优化后 | **110.7 MB** | **+29.7 MB** |
| 差值 | **−8.1 MB** | −7.8 MB |

空目录仍是 93.0 MB（不含条目，符合预期）。万项目录距 120 MB 阈值的余量
由 5.4 MB（按 9.2 的 114.6）回到 **9.3 MB**（按本表 110.7），
仍不足以覆盖 M1 的标签页与右键菜单，但已把"预算被框架吃掉 68%"这个事实摆到了台面上：
81 MB 框架底是 WPF 的固定成本，任何基于 WPF 的文件管理器都要先付这笔钱。

**由此产生的决定：阈值修订而非继续压缩。** 可支配部分只有 12 MB + 数据层增量，
优化的下一刀只能砍功能。已于当日按 ADR-0002 把 NF-05 上调为 150 / 185 / 230 MB，
并新增相对增量门禁 NF-05R ≤ 45 MB（当前 29.7 MB）。详见 §9.7 与 `docs/adr/0002-memory-budget.md`。

### 9.3 内存口径（必须固定，否则数字无法比较）

| 口径 | 值 | 说明 |
|---|---|---|
| **私有提交**（NF-05 判定用） | 114.6 MB | 对应任务管理器"提交大小"列，是本项目采用的判定基准 |
| 工作集（含共享） | 166.6 MB | 含 `PresentationFramework` 等与其他 WPF 进程共享的页，虚高 50 MB，仅参考 |

用含共享页的工作集会得出"超标 46 MB"的错误结论——同一台机器上再开一个 WPF 程序，
这 50 MB 不会翻倍，因为它本来就是共享的。

### 9.4 三条结论

**1. 10000 项只增加 9.6 MB（93.0 → 102.6）。** 说明虚拟化与 `FileEntry` 的轻量设计是有效的：
每个条目约 1 KB，且只创建可视区域内的项容器。这项风险可以关闭。
（9.2.1 的优化把这个增量进一步压到约 7.7 MB。）

**2. 基础占用 93 MB 才是大头，但其中 81 MB 是 WPF 框架底。** 空窗口对照证明：
本项目可支配的只有 12 MB。所以"降低基础占用"的天花板就是 12 MB，
不可能靠精简资源字典腾出几十 MB——此前的估算（资源字典占 20–30 MB）是错的。

**3. 首屏 233 ms 里枚举只占 66 ms。** 剩余约 167 ms 是 WPF 布局与 `ItemsControl` 首次填充，
属于框架成本。想再压只能减少行模板复杂度，收益有限。

### 9.5 遗留风险

- **内存预算已按 ADR-0002 修订，但三条配套约束尚未实现。** 非活动标签页不保留条目集合、
  右键菜单按需创建、预览解码限尺寸——这三条是 150 MB 档成立的前提，M1 对应批次必须落实，
  否则 10 个标签页各留一万项就是 77 MB，任何阈值都拦不住。
  → 2026-11-06 实测校正：这份估算按"每份 6.4 MB"外推，实测单份约 3 MB（双窗格只多 2.8 MB，
  见 §9.8.3）。结论不变（该做的事还得做），但**不要拿 77 MB 当"必须砍标签数"的依据**。
- **首屏有单次长帧**（max 92.9 ms），出现在滚动跨越到新区域时，来自项容器批量创建。
  平均帧率不受影响，M1 若加入缩略图需重新评估。
- **测量环境存在两态**，见 9.6。这是本轮最耗时的坑，判错会得出完全相反的优化结论。

### 9.6 测量环境的两态（判定内存数字是否可信）

同一台机器、同一个 exe、同样的操作，私有提交会在两个值之间跳，相差约 36 MB：

| 状态 | GDI 对象 | 句柄 | 空窗口私有提交 | 万项目录私有提交 |
|---|---|---|---|---|
| 正常态 | 56 | ~950 | 81 MB | ~110 MB |
| 高态 | 148 | ~1260 | 118 MB | ~144 MB |

三件事已经确认：

1. **与代码无关。** 空窗口对照程序同步变化，而它不含任何业务代码。
2. **不会自行回落。** 等 12 秒重测仍是高态，只有重启系统才恢复。
3. **两个状态内部各自稳定。** 正常态三次 109.6 / 111.7 / 110.7；高态三次 143.5 / 143.6 / 143.9。

由此产生的两条纪律：

- **GDI 对象超过 80 即判为高态，内存指标作废。** `Measure-List.ps1` 已内置该判定，
  高态时输出"不可判定"并返回退出码 3，不给出通过/未通过的结论。
- **空窗口对照超过 90 MB 同样判为高态**（2026-11-05 补，见 ADR-0008）。这条比 GDI 更可靠：
  高态下空窗口稳定在 118，而 GDI 在 118–120 之间跳。更关键的是，高态下 **`-Normalize` 会失效**——
  实测第 2–3 轮 Lingpane 私有提交 159.1 / 160.7 MB、空窗口 118.0 MB，相减得 41.1 / 42.7 MB
  看起来"正常"，但同一批里 Lingpane 自身在 121.8–160.7 之间摆了 39 MB。
  两态模型不够细：高态内部还有一层与进程启动时机相关的抖动，相减消不掉。
- **跨态的数字不能相减。** 本轮曾把"优化前 109 MB、优化后 143 MB"归因为某一行
  XAML 绑定，交替测量 12 次后证明两版本完全一致，真实原因是测量期间系统从正常态切到了高态。
  任何一次"改完变差/变好"的结论，都必须用同一状态内的交替测量复核。

排查过程中另外确认的两件事（均已写入工具）：

- **首次启动的私有提交明显偏高**（同一个空窗口首轮 118 MB，稳定后 81 MB），
  所以 `Measure-List.ps1` 增加了 `-Warmup`（默认 1 次，不计入结果）。
- **探针自身会污染句柄计数**：原先每 30 帧调用一次 `Process.GetCurrentProcess()`，
  每次都会打开一个进程句柄且未释放。已改为缓存单个实例。

### 9.7 内存门禁（ADR-0002 后的现行口径）

两条门禁并存，分工不同，**不可混用**：

| 门禁 | 定义 | 阈值 | 当前实测 | 超标含义 |
|---|---|---|---|---|
| **NF-05R**（相对，先看） | Lingpane 私有提交 − 纯 WPF 空窗口私有提交（单窗格、10000 项、滚动 240 帧） | ≤ 65 MB（2026-11-05 由 45 上调） | 44.8 MB | 代码回归，查数据层与视图层 |
| **NF-05H**（托管堆，降级判据） | 滚动结束后的 `GC.GetTotalMemory(true)`（单窗格、10000 项） | ≤ 12 MB | **5.8 MB**（2026-11-06 首次实测） | 数据层回归，与框架底和环境两态无关 |
| **NF-05**（绝对，后看） | Lingpane 私有提交总量 | 单窗格 150 / 双窗格 185 / 预览窗格 230 MB | 124.8 MB | 功能预算超支，砍功能或优化 |

NF-05R 的双窗格档为 90 MB（ADR-0008 新增）。**90 是估算值，双窗格开工前必须单独实测一次。**
→ 已实测（2026-11-06）：同态下双窗格相对增量 39.2 MB，距 90 有 2.3 倍余量，阈值不调整。详见 §9.8。

判定顺序固定为**先相对、后绝对**。理由是绝对值同时受框架底（81 MB）与测量环境两态
（±36 MB）影响，单独看会把框架成本或环境波动误判成代码问题；相对值把这两项都抵消掉了。

### 9.7.1 阈值变更历史

| 日期 | NF-05R 阈值 | 当时实测 | 依据 |
|---|---|---|---|
| 2026-11-03 | 45 MB | 29.7 MB | ADR-0002 首次设定，留 50% 增长空间 |
| 2026-11-05 | **65 MB** | 44.8 MB | ADR-0008：M1 批 3 功能（右键菜单、文件操作、拖放、命令、图标、i18n）使增量涨到 43–46，45 已无余量，单轮即超标 |

**每次发版都要把实测值追加到本表。** 下一版相比上一版涨幅超过 10 MB 时人工追查——
固定阈值只能拦住大幅回归，版本快照才能拦住"每版涨一点"的缓爬。

2026-11-06 复核双窗格与托管堆，**未调整任何阈值**：双窗格实测远低于 90 MB 档，NF-05H 有约 2 倍余量。
调阈值只能往松或往紧各走一步，两边都没有数据支撑。

### 9.8 双窗格与 NF-05H 首批实测（2026-11-06）

#### 9.8.1 怎么测的（工具已落地，不是一次性脚本）

探针新增 `--perf-split <第二目录>`：先分屏、把第二窗格导航到该目录，再按原流程测主窗格。
`Measure-List.ps1` 新增 `-SplitPath`，传入即自动套用双窗格档阈值（185 / 90），不需要手改参数。

```powershell
# 单窗格
pwsh tools/perf-fixture/Measure-List.ps1 -Exe publish/Lingpane.exe -Path D:\perf-10k -Runs 5 -Normalize
# 双窗格（第二窗格给另一个万项目录，两个大目录同时常驻才是要测的场景）
pwsh tools/perf-fixture/Measure-List.ps1 -Exe publish/Lingpane.exe -Path D:\perf-10k `
    -SplitPath D:\perf-10k-b -Runs 5 -Normalize
```

两个实现细节值得记下来，否则以后测出来的数字会被误读：

- **分屏在探针内部完成，且不写设置。** 走 `ToggleSplit()` 会把 `layout.splitEnabled = true`
  并立刻落盘，跑五次测量就让用户下次启动"莫名其妙分屏"。探针走 `EnterProbeSplit()`，
  只改内存中的形态。
- **分屏后活动窗格钉回主窗格**（`Tab.ActivatePane(0)`）。`Vm` 就是 `Tab.ActivePane`，
  不钉回去时后面所有指标都可能取自第二窗格。
- **第二窗格条目数为 0 时整轮作废。** 脚本显式给"不可判定"，避免"单窗格 + 一个空壳"
  被当成双窗格达标。

#### 9.8.2 实测数据

环境：Windows 10.0.26300 · .NET 9.0.22 · R2R · 240 帧 · 5 次中位 · **高态**（见下）。

| 场景 | 条目 | 私有提交 | 空窗口 | 相对增量 | 托管堆 | 句柄 | GDI |
|---|---|---|---|---|---|---|---|
| 单窗格 | 10000 | 145.4 MB | 108.0 MB | 36.4 MB | 5.8 MB | 1209 | 241 |
| 双窗格 | 10000 + 10000 | 148.2 MB | 108.0 MB | 39.2 MB | 5.4 MB | 1249 | 241 |

单窗格三次独立复测（36.4 / 36.6 / 35.3）与首次五轮（36.5 / 35.3 / 38.4 / 38.6 / 37.9）一致，
离散度在 3 MB 内；双窗格五轮 43.5 / 41.5 / 39.2 / 39.2 / 36.1，同样稳定。

#### 9.8.3 三条结论

1. **NF-05H 第一次有数：5.8 MB，阈值 12，余量约 2 倍。** 之前表里写"待测"不是"通过"，
   现在可以写"通过"。它的价值在于环境高态时仍可比——本轮就正好用上了。
2. **双窗格多一份万项数据层，只多 2.8 MB 私有提交，托管堆没有增长。**
   §9.5 里"12 个标签各留一份 `Entries`、一万项约 77 MB"是按每份 6.4 MB 线性外推的，
   实测单份约 3 MB，这条估算偏保守。保守不是错，但它不该被当成"必须砍标签数"的依据
   ——真正撑起 90 MB 档的是 0.2.0 的功能预算，不是当前这份数据层。
3. **首屏数字不可跨档比较。** 双窗格首屏 116 ms 比单窗格 172–183 ms 更快，
   不是分屏带来的收益：探针在分屏之后才导航主窗格，此时窗口已完成首轮布局，
   而单窗格档的首屏把窗口自身的首次布局成本也算进去了。同一份代码、同样的目录，
   只因为测量顺序不同就差 60 ms。

#### 9.8.4 本轮处于高态，绝对值仍不可判定

空窗口对照 108–110 MB（判定线 90）、GDI 241（判定线 80），全程高态。按 §9.6 的纪律：

- NF-05 与 NF-05R 的**阈值判定无效**，脚本已返回退出码 3；
- 表里的相对增量只可用于**同态内**的单/双对照，**不能与历史 44.8 MB 相比**；
- NF-05H 不受影响，5.8 MB 这个数在低态下只会更低（数据层与框架底无关）。

下一版若在低态下复测，应把结果追加到本表并注明环境态——**跨态相减是 §9.6 明令禁止的**。


分档上调的依据与配套约束见 `docs/adr/0002-memory-budget.md`。要点：
框架底 81 MB 是 WPF 的固定成本，原 120 MB 阈值只留 39 MB 给业务功能，
压缩空间已被摸到天花板（优化后仅省 8.1 MB），因此改阈值而非继续压缩。

## 11. 环境变慢与代码回归的区分

启动变慢有两个完全不同的原因，处置方式相反。判错方向代价很高：把环境问题当成代码回归，
会去改本来没问题的代码；把代码回归当成环境问题，会漏掉真实退化。

### 11.1 三步判定

1. **看离散度**。大于 1.5 说明测量期间系统负载在变化，静置或重启后重测，不要看结论。
2. **跑最小 WPF 空窗口对照**（`tools/env-check`）。若空窗口 P50 也超过 800 ms，
   说明这台机器当前跑任何 WPF 程序都慢，Lingpane 的数字不可信，不要动代码。
3. **空窗口正常而 Lingpane 超标**，才是代码问题。查启动路径的同步 IO、资源加载、
   启动期初始化，见 §8。

### 11.2 2026-11-03 的实例

同一天下午，同一份二进制（未做任何代码改动）连续测出相差一倍的数字：

| 时间 | Lingpane P50 | 空窗口 P50 | 离散度 | CPU | 可用内存 |
|---|---|---|---|---|---|
| 15:47 | **511 ms** | 516 ms（485–571） | 1.10 | 29% | 51% |
| 16:05 | **1 102 ms** | 1 150 ms（1 095–1 191） | 1.13 | 32% | 48% |
| 16:40 | 556 ms | 516 ms | 1.18 | 54% | 48% |

第二组的迷惑性在于**环境指标全部正常**：CPU 32%、内存 48%、CPU 性能 163%（超频）、
磁盘队列 0、无杀毒进程、高性能电源方案。单看这些会认为环境没问题，于是把 511 → 1102
判定为严重回归。

实际是整机 WPF 慢了一倍——空窗口只有 10 行代码，也测出 1 095 ms。约 20 分钟后自行恢复，
期间没有做任何修复动作。

**教训：CPU、内存、频率这些指标正常，不等于 WPF 的运行条件正常。** 只有跑一个不含
业务代码的对照程序，才能把"框架层成本"和"自己代码的成本"分开。

### 11.3 对照工具

```
pwsh tools/env-check/Measure-Baseline.ps1 -Runs 10
```

编译一个最小 WPF 空窗口（同样关闭 IME，与 Lingpane 一致），测 P50。判据：P50 ≤ 800 ms
为环境正常（本机正常值 485–665 ms，留余量）；超过则环境异常。

### 11.4 判断"这次改动是否引入回归"的正确做法

历史数字不能用来判断回归。2026-11-04 下午出现过一次典型案例：

| 对象 | 上午 | 下午 |
|---|---|---|
| 上一提交的二进制（未改一行代码） | 499 ms | **743 ms** |
| 当轮改动的二进制 | — | 749 ms（同一测量窗口内） |

只看"499 → 749"会误判为 +250 ms 严重回归；实际上**同一份旧二进制在同一时刻也是 743 ms**，
即整机对这类进程变慢了，与代码无关。

因此判定回归只有一种可靠方式：**用 `git worktree` 检出上一提交、单独编译，与当前版本交替测量**。

```bash
git worktree add /d/tmp/lingpane-head <上一提交>
dotnet publish /d/tmp/lingpane-head/src/Lingpane.App -c Release -r win-x64 -o /d/tmp/lingpane-head/out
# 然后对两个 exe 交替跑 Measure-Startup，比对 P50
git worktree remove /d/tmp/lingpane-head --force
```

判据：两版 P50 差在 ±10% 内即视为无回归，绝对值超标交给 §11.1 的对照程序处理。

`tools/startup-bench/Measure-Startup.ps1` 在判定未通过且离散度正常时，会自动提示先跑
这个对照——因为"数据很稳、但整体偏移"，正是环境变慢的典型特征。
