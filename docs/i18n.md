# 多语言（中/英）实现方案

> 对应 `docs/requirements.md` FR-10.4、AC-11。阶段：**0.1.0 收尾，M2 开工前**。

## 一、目标与硬约束

| 项 | 要求 | 来源 |
|---|---|---|
| 语言 | 简体中文（`zh-Hans`）/ English（`en`） | FR-10.4 |
| 选择方式 | 跟随系统，可手动覆盖 | FR-10.4 |
| 切换耗时 | <200ms，**不重启** | FR-10.4 |
| 覆盖率 | 界面文字全部走资源，无硬编码 | FR-10.4 / AC-11 |
| 启动成本 | ≤5ms 埋点增量，否则视为回归 | NF-01 / NF-08 |
| 依赖 | 不引入 NuGet 包（`resx` 是 MSBuild 内置能力） | §9.1 技术栈收敛 |

**为什么排在 M2 之前：** 当前待抽取文案约 210 处；M2 的标签栏、双窗格、预览窗格、主页至少再加 1.5 倍。
抽取成本与文案量线性相关，且已有硬编码不动，越晚做越贵。反过来，i18n 落地后 M2 的新界面天然按资源键写，
不会产生第二批硬编码。

## 二、方案选型

| 方案 | 运行时切换 | 类型安全 | 工具链（译者可用） | 结论 |
|---|---|---|---|---|
| A. 每语言一份 XAML `ResourceDictionary` + `DynamicResource` | ✅ 换字典即刻生效 | ⚠️ 键是字符串，拼错表现为空白，无编译期检查 | ❌ 译者要改 XAML | 备选 |
| B. `.resx` + `x:Static` 强类型引用 | ❌ `x:Static` 是编译期静态值，换语言必须重建窗口 | ✅ | ✅ | ❌ 不满足 <200ms |
| C. **`.resx` 单一数据源 + 自定义 `TrExtension` → 绑定到带索引器的 `LocalizationService`** | ✅ 改 `CultureInfo` + 触发一次 `PropertyChanged`，全部绑定重取 | ✅ 代码侧强类型；XAML 侧键名有 CI 校验 | ✅ 标准 resx，可用任意翻译平台 | ✅ **采用** |
| D. 自建 JSON/字典 | ✅ | ❌ | ❌ 无工具链 | ❌ |

方案 C 的关键：`{loc:Tr Key=X}` 不是返回一个字符串，而是**返回一个 `Binding`**，绑到
`LocalizationService` 的索引器 `this[string key]`。语言一变，索引器值变，`INotifyPropertyChanged` 一响，
界面上所有这类绑定同时刷新——不需要重建窗口，也不占用启动路径。

## 三、目录与文件

```
src/Jianlan.Core/Localization/
  Strings.resx                 # 中性资源 = 英文（en），源语言
  Strings.zh-Hans.resx         # 简体中文
  Strings.Designer.cs          # MSBuild 生成（PublicResXFileCodeGenerator）
  LocalizationService.cs       # Culture 管理、索引器、切换事件、回落
src/Jianlan.App/Localization/
  TrExtension.cs               # {loc:Tr Key=...} → Binding
tools/i18n/
  check-keys.py                # 键一致性校验（CI 用）
  pseudo-loc.py                # 伪语言生成（走查用）
```

### 必须先改的一行

`Directory.Build.props` 当前：

```xml
<SatelliteResourceLanguages>en</SatelliteResourceLanguages>
```

这行的作用是**只保留英文卫星程序集，其余丢弃**。加上中文卫星后，它会把 `zh-Hans/Jianlan.Core.resources.dll`
裁掉——语言切过去一片英文。改为：

```xml
<SatelliteResourceLanguages>en;zh-Hans</SatelliteResourceLanguages>
```

**中性资源定英文**而不是中文：开源项目默认语言应为英文（README、issue、外部贡献者都在这条线上），
且中性资源直接编进主程序集，英文用户零探测；中文走卫星程序集，多一次同目录文件探测（约 1ms）。
若反过来（中性=中文），中文用户快 1ms、英文用户慢 1ms，但在仓库里会形成"源语言是中文、翻译是英文"的
反常结构，代码评审与外部贡献的成本更高。

### 键命名

`区域.控件.语义`，全英文，禁止用文案本身当键：

```
Menu.File.Rename
Menu.Edit.CopyPath
Settings.Appearance.Theme
Settings.Appearance.Theme.FollowSystem
Error.PathNotFound
Error.AccessDenied
Prompt.NewFolder.Title
Status.SelectedCount          // "已选中 {0} 项"
About.Version                 // "版本 {0}"
```

占位符统一 `{0}` 序号形式。**不要**把带单位/复数的整句拼起来——中英文语序不同，只能整句一条键。

## 四、运行时切换怎么做

`LocalizationService`

```
Apply(CultureInfo culture)
  ├─ CultureInfo.DefaultThreadCurrentUICulture = culture
  ├─ CultureInfo.DefaultThreadCurrentCulture     = culture   // 日期/数字格式跟随
  ├─ Thread.CurrentThread.CurrentUICulture       = culture
  ├─ _culture = culture
  └─ OnPropertyChanged("Item[]")   // 索引器绑定刷新
     OnPropertyChanged(null)       // 兜底：WPF 对 null/empty 走"全部重取"
```

- 只影响 UI 线程创建的绑定；WPF 里 `DynamicResource`/`Binding` 都跑在 UI 线程，无跨线程问题。
- 非 UI 线程（枚举、复制、计算大小）取文案时用 `Strings.X` 属性——`ResourceManager` 按 `CurrentUICulture`
  取，**必须在调用线程设好 culture**，否则后台线程拿到的是进程默认。这点容易漏：`Task.Run` 里的错误消息
  会退回英文。做法：`LocalizationService` 在 `Apply` 时同时设置 `DefaultThreadCurrentUICulture`（已含），
  新线程继承该默认值，不需要每个 `Task.Run` 手动传。
- 刷新代价：一次全量绑定重算。按当前窗口规模（约 300 个可见绑定）实测 <50ms，满足 <200ms。
  0.2.0 有标签页后，只刷新活动窗口，非活动标签在激活时刷新。

### XAML 写法

```xml
<TextBlock Text="{loc:Tr Key=Settings.Appearance.Theme}"/>
<Button Content="{loc:Tr Key=Menu.File.Rename}"
        ToolTip="{loc:Tr Key=Menu.File.Rename.Tip}"/>
```

`TrExtension.ProvideValue` 返回：

```csharp
new Binding($"[{key}]") { Source = LocalizationService.Instance, Mode = OneWay }
```

键不存在时索引器返回 `!{key}!`（醒目的占位），而不是空串——空串会被当成"设计如此"漏过走查。

### 代码里写

```csharp
Strings.Error_PathNotFound          // 强类型，键名拼错编译不过
string.Format(Strings.Status_SelectedCount, n)
```

菜单标题、命令名、快捷键提示统一从 `Strings` 取。注意 `KeyBindings` 里的 `GestureText`（`"Ctrl+C"`）
**不参与翻译**，它是键名不是文案。

## 五、语言选择逻辑

设置项放 `general.language`（新增到 `settings.json`，同时更新 `docs/settings-schema.md`）：

| 值 | 行为 |
|---|---|
| `auto`（默认） | `CultureInfo.InstalledUICulture`——用"系统安装语言"，不用 `CurrentUICulture`（后者可能被父进程/兼容设置改掉）。`TwoLetterISOLanguageName == "zh"` 判中文，其余一律英文 |
| `zh-Hans` | 强制中文 |
| `en` | 强制英文 |

- 应用时机：读完 `settings.json` 之后、创建视图模型之前（`App.OnStartup` 里，`settings` 段之后）。
  成本约 1ms，计入启动埋点。
- 无法识别的值（用户手改坏了）→ `auto`，不报错。
- 切换语言后立刻写回 `settings.json`（与其它设置同一套原子写）。

## 八、布局风险（英文比中文长）

英文字符串普遍比中文长 30–50%，固定宽度会截断。改动清单：

| 位置 | 现状 | 处理 |
|---|---|---|
| 设置页字段标签 + 控件 | 部分 `Width=300` 固定 | 标签改 `MinWidth`，控件 `Width` 保留（输入框宽度不该随语言变） |
| 右键菜单 | 宽度自适应 | 无风险，但 `GestureText` 对齐列要留够 |
| 删除确认对话框 | 文案单行 | 改 `TextWrapping="Wrap"` + `MaxWidth` |
| 工具栏按钮 ToolTip | 自适应 | 无风险 |
| 状态栏 | 单行 `TextBlock` | 加 `TextTrimming="CharacterEllipsis"` + `ToolTip` 全文 |
| 列头 | 固定列宽 | 「修改日期」列英文 `Date modified` 更宽，`layout.columnDateWidth` 默认值按语言给（中文 120 / 英文 150） |

`AC-11` 走查清单（英文下逐项看）：设置窗口全部分节、主窗口工具栏与列头、右键菜单、新建/重命名对话框、
删除确认、错误提示（无权限 / 文件占用 / 路径不存在）、关于页、状态栏。

## 九、格式化的两个隐藏坑

1. **名称排序**：`EntrySort` 目前名称比较用什么口径要确认。多语言下应固定为
   `StringComparer.CurrentCultureIgnoreCase`——中文系统按本地规则、英文系统按本地规则，
   符合各自用户预期；`OrdinalIgnoreCase` 在中文下会把中文排在英文后面（按码位），观感是"排序坏了"。
   自然序（`file2 < file10`）的数字分段比较不受文化影响，保持不变。
2. **日期与大小**：日期用 `CurrentCulture` 短格式（`2026/11/5` vs `11/5/2026`），列宽会变；
   大小单位（`KB/MB/GB`）**不译**，只译"计算中…""部分结果"这类状态文字。

系统级对话框不受我们控制：属性页、系统 Shell 右键菜单、文件选择框始终跟随**系统语言**，
不随应用设置变化。这一点要写进文档与 FAQ，否则会被当成 bug 报上来。

### 落地时与方案不同的三处

1. **强类型访问器自己生成**：MSBuild 的 `StronglyTyped*` 产出 `internal class Strings`，跨程序集
   （App 项目）访问不到。改为 `tools/i18n/gen-strings.py` 从 resx 生成 `Strings.g.cs` 并提交进仓库；
   `check-keys.py` 会校验生成物与 resx 同步，改了文案忘了重新生成会直接报错。
2. **`TypeText` 去掉了缓存**：原来按需缓存字符串省内存，但语言一切换，已显示过的行会停在旧语言。
   改为每次计算——虚拟化下只有真正渲染的行才会取，代价可忽略。
3. **命令标题走工厂**：`AppCommand.Title` 是 init-only，无法在切换后更新。新增 `TitleFactory`，
   `ResolveTitle()` 每次读取都取当前语言。

### 剩余工作（按文件）

设置页已清零：`SettingsWindow.xaml` 与 `.xaml.cs` 的界面文案全部走资源键，`check-keys.py`
残留硬编码为 0。剩下两处在 `MainWindow.xaml.cs`：一处是注释（已改为独占行，工具不再误报），
一处是热键注册失败日志（`// i18n-ignore`，只进 `app.log`）。

日志与崩溃记录（`CrashLogger`、`SingleInstanceGuard`、`SettingsStore`）已用文件级
`i18n-ignore-file` 豁免：这些文本只进日志文件、不进界面，保持单语更利于对外报问题。

**英文走查发现并修掉的布局问题**：`Text.FieldHint` 原来不换行，英文提示超过宽度后被
省略号截断（"…applies to this session o…" / "…When off, the next l…"）。改为
`TextWrapping="Wrap"` + `TextTrimming="None"`，中文不受影响（本来就短）。

**切换验证方法**：探针启动时按 `settings.json` 的语言显示窗口，渲染完成后再切换，
外部截图看到的就是"同一进程内换语言"的结果。`JIANLAN_PERF_LANG` 支持逗号分隔的
多次切换——只切一次测不出第二次是否因绑定逐层失效重算而变慢，AC-11 要求的是连续 3 次：

```bash
# 连续切 3 次：预计 26 / 15 / 13 ms
JIANLAN_PERF_LANG=en,zh-Hans,en Jianlan.exe --perf-probe <目录> --perf-frames 0
# perf-probe.json 里的 languageSwitchMsList / languageSampleText / languageAfterSwitch 即证据
```

注意：`Ctrl+,` 依赖全局热键，而**探针模式刻意不注册全局热键**（避免抢用户的组合键），
所以探针进程里打不开设置页。设置页走查要用真实语言设置启动，再用 `window_drive.py`
的 `WD_TITLE` 选窗口、`wheel` 滚到下半屏：

```bash
python tools/window-drive/window_drive.py <pid> keys ctrl+comma
WD_TITLE=Settings python tools/window-drive/window_drive.py <pid> screenshot out.bmp
WD_TITLE=Settings python tools/window-drive/window_drive.py <pid> wheel -120 16
```

## 十二、伪语言走查

`check-keys.py` 只能发现源码里显而易见的中英文常量，发现不了几类漏网：C# 里拼接出来的
句子、XAML 里 `<Run>` 的零散文字、以及第三方控件自带的内建文案。伪语言走查补的就是这一层。

**做法**：把资源整体换成带重音、拉长 40% 的假文字，界面上一旦还剩正常英文或中文，
就说明那段没走资源键。

```bash
python tools/i18n/pseudo-loc.py          # 生成 Strings.qps-ploc.resx（生成物，不入库）
dotnet publish src/Jianlan.App -c Release -r win-x64 --self-contained false \
  -p:IncludePseudoLoc=true -o <独立目录>
JIANLAN_PERF_LANG=qps-ploc Jianlan.exe --perf-probe <目录> --perf-frames 0
```

三个细节值得记下来，否则会白跑一轮：

- **字符**：字母映射成 `á ç ð š` 这类近形字，正常英文里不会出现；每个元音重复一次，
  整体膨胀约 1.35 倍，正好压测版式（比德语还长一点）。
- **占位符**：`{0}` 必须原样保留。第一版 `re.split` 的分隔符没写捕获组，`{0}` 被自己的
  分隔逻辑吃掉了，标题直接变成 `[ - Jianlan]`。现在脚本逐条比对占位符，对不上就报错退出。
- **边界**：每行首尾加 `[ ]`。看到缺一侧括号，说明那行被裁掉了，而不是文案本身有问题。

**编入策略**：伪语言只在 `-p:IncludePseudoLoc=true` 时进卫星程序集
（`Directory.Build.props` 的条件 `SatelliteResourceLanguages` + `Jianlan.Core.csproj`
里对 resx 的 `Remove`），正式发布包不会多出一个语言目录。

**结果**：主窗口（工具栏、列头、状态栏、导航栏）、右键菜单、删除确认、属性提示
全部为伪文字，无裸英文或中文残留。**发现一个真缺陷**：运行中切换语言后，列表
"类型"列仍停在旧语言。

### 走查发现的两个问题（已修）

**类型列不跟随语言切换**。`FileEntry.TypeText` 本身不缓存、每次按当前语言计算，
但 WPF 绑定只在收到 `PropertyChanged` 时才重取。结果：切换语言后，已经渲染过的行
一直显示旧语言的"文件夹"。修法是 `FileEntry.RefreshTypeText(entries)` 批量通知一次，
与既有的 `SetShowExtensions` 同一套路——只有可视行真有订阅者，万项遍历开销可忽略。

**系统按钮跟系统语言，不跟应用语言**。`MessageBox` 的按钮文字由 Windows 系统语言决定：
中文系统上把界面切成英文，属性窗口仍是「确定」、删除确认仍是「是(Y)/否(N)」，
整窗英文里夹两个中文按钮。改用自绘的 `ConfirmWindow`（按钮走 `Dialog.Yes/No/Ok`），
中英文各自正确，顺带能控制英文长文案的换行与按钮最小宽度。

### 走查工具的两处补充

- `WD_HWND`：直接指定窗口句柄。右键菜单、下拉菜单是独立 HWND，既没有标题也小于
  主窗口，按标题和按面积都取不到。
- `rclick <x> <y>`：右键必须用真实鼠标事件。投递 `WM_RBUTTONUP` 不弹菜单——
  WPF 打开 ContextMenu 前会检查真实按键状态。

## 十四、后台错误提示走查（ACL 失败）

AC-11 的最后一条：后台线程产生的错误提示必须跟随界面语言。这一条只能靠真实失败来验，
构造两个夹具目录即可，不需要断网或拔盘。

| 夹具 | 构造 | 触发 |
|---|---|---|
| `aclnowrite` | `icacls <dir> /deny "<用户>:(WD,AD)"` | 新建文件夹 → `Directory.CreateDirectory` 抛异常 |
| `acldeny2` | `icacls <file> /deny "<用户>:(D)"` | 回收站删除 → `SHFileOperation` 返回非 0 |

**修复前实测（中文界面）**：

```
新建文件夹失败：Access to the path 'D:/ac05/aclnowrite/新建文件夹' is denied.
删除失败：删除失败（Shell 错误 0x78）
```

两类问题：前半句是资源键（跟随应用语言），后半句是运行时异常原文（跟随**系统语言**），
于是中文界面里永远夹一句英文；删除那条还把未文档化的十六进制码直接摆给了用户，
违反 `docs/logging.md` §6。

### 三处修改

1. **异常文本进不了界面**。新增 `Core/FileSystem/FsErrors`：按异常类型与 Win32 码归到
   `E1001`–`E1007`，界面只显示该码的译文；原文连同错误码写 `app.log`。
   接上 `Core/Diagnostics/LogSink`（App 启动时把 `AppLog.Warn` 挂上去），
   这样 Core 不必反向引用 App 也能留痕。
2. **删除失败不再暴露 Shell 码**。`SHFileOperation` 的返回码混了 `DE_*` 与 Win32 两段，
   部分值未文档化。改为回到文件本身试开一次句柄，用异常区分"被占用 / 没权限"，
   判不出来时给一句通用人话（`E1007`），十六进制码只进日志。
3. **失败提示被刷新覆盖**。删除/粘贴/拖放完成后会刷新目录，而刷新会按新目录重算状态栏，
   把刚写进去的失败原因冲掉——用户只看到"1 项 · 枚举 2 ms"，根本不知道失败过。
   现在刷新后把失败文案重新写回。

### 修复后实测

| 语言 | 新建失败 | 删除失败 |
|---|---|---|
| 中文 | `新建文件夹失败：没有访问权限` | `删除失败：没有访问权限` |
| 英文 | `Could not create folder: Access denied` | `Delete failed: Access denied` |

日志侧（与界面语言无关，始终单一语言）：

```
[WRN] fs.createFolder code=E1002 msg="D://ac05//aclnowrite · UnauthorizedAccessException: Access to the path '...' is denied."
[WRN] fs.delete       code=E1002 msg="shell=0x78 · D:/ac05/acldeny2/only.txt"
```

**注意**：`.NET` 的框架异常消息并不跟随 `CurrentUICulture`——`Apply()` 设了
`DefaultThreadCurrentUICulture` 也没用，因为运行时语言包只装了系统语言那一套。
所以"把异常原文拼进界面"在任何语言下都不可靠，必须走错误码。
