# 彩色标签（FR-4）存储方案复核

- 结论：**不需要 SQLite。** 用"内存索引 + 追加日志（JSONL）"覆盖 FR-4.2 全部九条要求，且更快、更省。
- 状态：建议修订 `docs/requirements.md` FR-4.2.1（原文写死 SQLite）
- 测量日期：2026-11-05
- 测量口径：私有提交（`PrivateMemorySize64`），与 `performance-gate.md` §9.3 一致

---

## 1. 为什么值得复核

需求文档把存储方案写成"已定"，但定的是**数据模型**，不是**存储引擎**：

> 键 `(VolumeSerial, FileIndex)`，冗余路径；重命名、同卷移动后仍生效；跨卷移动丢失（需明示）。

这个模型是对的，没有争议。真正有争议的只是"这堆键值对存在哪儿"——
原文一句"本地 SQLite 单文件存储"把它带过去了，没有给理由。

而引入 SQLite 的代价是具体的：

| 代价 | 量 | 影响 |
|---|---|---|
| 运行时第三方依赖 | 从 0 个变成 2 个包（`Microsoft.Data.Sqlite` + `SQLitePCLRaw`） | 项目至今 `csproj` 里零 `PackageReference`（ADR-0004 连 DI 容器都不引入） |
| 包体 | publish 当前 25 MB，NF-07 上限 30 MB | 原生 `e_sqlite3.dll` 约 1.4 MB，余量从 5 MB 缩到 3.6 MB |
| 内存 | 实测 **+12.0 MB** 私有提交（见 §3） | NF-05R 目前只剩 1–2 MB 余量（见 §4） |
| 合规 | AC-10 依赖清单从"两个框架条目"变成"要写 SQLite 的版权、许可证、版权声明" | `gen-third-party.ps1` 从可选变必需 |

三条硬约束同时压着：内存几乎没余量、包体只剩 5 MB、合规本来就有缺口（`THIRD-PARTY-NOTICES.md` 还不存在）。在这个前提下引入一个 12 MB 的依赖，需要先证明它不可替代。

## 2. 标签数据的真实规模

先看要存多少东西，否则讨论引擎是空的。

一条标签记录：

| 字段 | 类型 | 典型大小 |
|---|---|---|
| VolumeSerial | uint32 | 4 B |
| FileIndex | uint64 | 8 B |
| 路径（冗余） | string | 40–120 B（中文路径按 UTF-16 计） |
| 颜色 | byte | 1 B |
| 修改时间（用于 FR-4.2.9 模糊重绑） | int64 | 8 B |
| **合计** | | **约 160–200 B/条** |

记录数按用户画像分档（这是估算，不是实测，但没有第二种办法得到——彩标还没实现）：

| 画像 | 标记数 | 文件大小 | 内存 |
|---|---|---|---|
| 轻度（只用"重要/待办"两色） | 50–200 | 8–32 KB | < 50 KB |
| 常见 | 500–2000 | 80–320 KB | 0.1–0.4 MB |
| 重度（素材库/摄影/代码归档整批标） | 5000–20000 | 0.8–3.2 MB | 1–4 MB |
| 极端（几乎整个盘都标） | 100000 | 16 MB | 20 MB（**需要设上限，见 §6**） |

**结论：这是一份"最多几 MB"的数据。** SQLite 的存在理由是"数据大到内存放不下、或需要复杂查询下推"，这里两个条件都不成立。

## 3. 实测对比（2026-11-05）

测量程序：`D:\ac05\sqliteprobe`（每个方案独立进程，避免私有提交的堆段残留污染基线）。
数据量 5000 条，路径为真实形态的中文长路径。

| 指标 | SQLite | 内存字典 + JSONL |
|---|---|---|
| 基线（仅 .NET 运行时） | 9.61 MB | 9.64 MB |
| 装入 5000 条后 | 14.59 MB（+4.98） | 9.36 MB（+0，托管堆实测 0.95 MB） |
| 模拟浏览查询后 | 21.57 MB（+11.96） | 10.39 MB（+0.75） |
| 释放连接/落盘后 | **21.57 MB（不归还）** | 11.54 MB（+1.90） |
| **净增私有提交** | **+11.96 MB** | **+1.90 MB** |
| 查询耗时 | 200 批 × 200 项 = 4 万次：**189 ms**（4.7 µs/次） | 10000 批 × 200 项 = 200 万次：**201 ms**（0.10 µs/次） |
| 文件大小 | 812 KB（含 WAL） | 753 KB |

三点值得注意：

1. **SQLite 贵 6.3 倍，而且不归还。** 连接 `Dispose()` 之后私有提交停在 21.57 MB 不动——
   原生堆和 page cache 提交给 OS 就不会退回。对一个常驻的内存预算来说，这 12 MB 是**永久成本**，
   不是峰值。而彩标是 P0 功能，用户一旦用过就一直开着。
2. **SQLite 反而更慢。** 4 万次查询 189 ms vs 200 万次 201 ms，每次差 47 倍。
   原因是每次 `IN (...)` 都要 prepare、绑 200 个参数、再 step；
   内存字典就是一次哈希查找。FR-4.2.4 那条"禁止逐项查询"的约束，
   在 SQLite 下是必须在 SQL 层解决的问题，在字典下**这个问题不存在**。
3. **`Microsoft.Data.Sqlite` 的内存大头不是缓存，是原生库。** 即使把 `cache_size` 调到最小，
   原生 SQLite 引擎本身（页面缓存、schema、编译后的 VM）也要几 MB。这不是调参能省掉的。

> 测量方法的坑：第一次把两个方案放在同一个进程里先后跑，得到"字典 +10.67 MB"的荒谬结果——
> 因为先跑的 SQLite 已经把堆段撑开，之后 GC 再清也不退给 OS，后测的方案继承了被污染的基线。
> 私有提交必须一个进程测一个方案。

## 4. NF-05R 的现状（决定了这 12 MB 有多致命）

2026-11-05 用 `Measure-List.ps1 -Normalize` 复测（10000 项 + 滚动 240 帧，5 轮取中位）：

| 轮次 | 枚举 | 首屏 | 帧率 | 私有提交 | 空窗口 | **NF-05R 增量** | GDI |
|---|---|---|---|---|---|---|---|
| 1 | 98 ms | 322 ms | 83.4 fps | 127.4 MB | 81.0 MB | **46.4 MB** ⚠️ | 81（低态） |
| 2 | 82 ms | 283 ms | 87.6 fps | 124.2 MB | 81.0 MB | **43.2 MB** | 81（低态） |
| 3 | 69 ms | 303 ms | 60.8 fps | 124.8 MB | 118.0 MB | 6.8 MB（高态，作废） | 118 |

- NF-05R 阈值 45 MB，实测落在 **43.2–46.4 MB**，**已经踩线，单轮即超标**
- NF-05 绝对档 150 MB，实测 124.8 MB，余量 25 MB
- 2026-11-03 时这个数字是 29.7 MB，两天涨了 13.5 MB，来自 M1 批 3 的功能（右键菜单、文件操作、拖放、命令系统、图标解析、i18n）

也就是说：**再塞 12 MB 的 SQLite，NF-05R 直接超到 56 MB。** 这个决定不能只从"哪个方案更正规"来判。

阈值重新标定见 §7。

> **2026-11-08 补记（重要，别被本节论证误导）**：2026-11-05 的 ADR-0008 把 NF-05R 阈值从 45 上调到 **65 MB**。
> 按新阈值，SQLite 的 44.8 + 12 ≈ 56.8 MB **不再超标**，本节"12 MB 直接顶穿"这条论据**已失效**。
> 最终结论（走 JSONL）不变，但支撑它的理由换成了另外三条，见 `docs/m2-plan.md` §4.5：
> 零 `PackageReference` 的架构约束、包体只剩约 5 MB 余量（NF-07）、4 万次查询快 47 倍。
> 引用本节时请只引数据（12.0 vs 1.9 MB 实测），不要引"会超标"这个推论。

## 5. 九条要求的覆盖情况

需求 FR-4.2 一共九条，逐条对照：

| 需求 | 原文要求 | 文件方案 | 谁的实现更简单 |
|---|---|---|---|
| FR-4.2.1 | 单文件存储 | 单文件 `tags.jsonl` | 相同 |
| FR-4.2.2 | File ID 主键 + 路径冗余 | 相同（模型不变） | 相同 |
| FR-4.2.3 | 延迟打开 | 首次访问才读文件 | 相同 |
| FR-4.2.4 | 批量查询可视区，禁止逐项查询 | 内存字典 O(1)，**该约束自动消失** | **文件更简单** |
| FR-4.2.5 | 未就绪先渲染，就绪后补标记 | 相同 | 相同 |
| FR-4.2.6 | 清理失效标签 | 后台遍历 + `File.Exists` | 相同 |
| FR-4.2.7 | 导出/导入 JSON | **原生格式，导出=复制，导入=读** | **文件更简单**（SQLite 要另写导出器） |
| FR-4.2.8 | 损坏自动备份重建 | 坏行跳过（自愈）+ 整体损坏备份重建 | 相同 |
| FR-4.2.9 | 同卷模糊重绑 | 内存扫描（几千条 < 1 ms） | 相同 |

九条全覆盖。其中两条（4.2.4、4.2.7）在文件方案下**反而更简单**——
因为它们本质上是"用 JSON 表达"和"随便查"，SQLite 的 schema 与 SQL 在这里是中间层。

唯一真正需要 SQLite 的场景是"标签数 > 10 万且要频繁按颜色+目录复合过滤"。需求里没有这一条，
FR-4.1.6（按标签筛选当前目录）是 P2，且筛选的是**当前目录**（几十到几千项），内存过滤足够。

## 6. 建议方案

### 6.1 存储格式：追加日志 + 周期性压缩

```
%LOCALAPPDATA%\Lingpane\data\tags.jsonl
```

每行一条**操作**，不是一条**状态**：

```jsonl
{"op":"set","v":438132814,"f":562949953421312,"p":"D:\\资料\\报告.docx","c":3,"t":1730000000}
{"op":"set","v":438132814,"f":562949953421313,"p":"D:\\资料\\预算.xlsx","c":1,"t":1730000001}
{"op":"del","v":438132814,"f":562949953421312}
```

- **写入**：`FileStream.Append` 一行 + `Flush(true)`，一次打标签最多丢最后一条（断电场景）
- **读取**：启动后首次访问标签时全量扫描，按 `(v,f)` 折叠成字典；坏行跳过，不整体失败
- **压缩**：行数超过"存活记录数 × 3 且 > 2000"时，后台重写为新快照（临时文件 + `File.Replace`，
  复用 `SettingsStore.Save` 已验证的原子写范式）
- **导出**（FR-4.2.7）：直接把当前快照写出去；导入则是逐行 apply

### 6.2 内存索引

```csharp
// Core/Tagging/TagStore.cs
private readonly Dictionary<(uint Volume, ulong FileIndex), TagRecord> _byId;
private readonly Dictionary<string, (uint, ulong)> _byPath;   // 路径 → FileId，用于浏览时命中
```

- 5000 条实测 0.95 MB 托管堆，可接受
- 一万项目录渲染时查 10000 次字典，耗时 < 1 ms（实测 200 万次 201 ms）
- **上限策略**：`_byId.Count > 50000` 时停止接受新标签，状态栏提示"标签数量已达上限"。
  这是显式降级，不是静默失败——20 MB 的标签库已经不是"标记"，是拿它当目录索引用

### 6.3 真正的风险不在存储，在枚举时取 FileId

这一条比选什么存储重要十倍，原文和规划都没写清：

**`FileSystemEnumerable`（`FindFirstFileEx`/`FindNextFile`）拿不到 FileId。**
`WIN32_FIND_DATA` 里没有 FileIndex 字段。要拿必须额外一次系统调用。

三种做法及其代价：

| 做法 | 代价 | 结论 |
|---|---|---|
| 每个条目 `CreateFile` + `GetFileInformationByHandle` | 一万项 = 一万次系统调用，枚举从 82 ms 涨到数百 ms | ❌ 直接击穿 NF-03 |
| 换 `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` 自己枚举 | 一次调用返回整批（含 FileId），但要自己处理 `FILE_ID_BOTH_DIR_INFO` 结构、缓冲区不足重启、长路径、UNC | ✅ 采用，约 1–2 天 |
| 打标签时才取 FileId，浏览时只按路径匹配 | 零枚举成本，但**重命名后标签失效**——恰好是数据模型要解决的核心问题 | ❌ 与 FR-4.2.2 冲突 |

**建议加一条优化：只在"该目录存在标签记录"时才走取 FileId 的慢枚举。**
绝大多数目录一条标签都没有，用现有快速路径；只有用户标记过的目录才付出额外成本。
判定方式很便宜：字典里按目录前缀查一次（`_byPath` 建一层目录前缀索引，或维护 `HashSet<string> taggedDirs`）。

## 7. 结论

| 项 | 决定 |
|---|---|
| 存储引擎 | **文件（JSONL 追加日志），不引入 SQLite** |
| 数据模型 | 不变：`(VolumeSerial, FileIndex)` 主键 + 路径冗余（FR-4.2.2 原样保留） |
| 运行依赖 | 保持零 `PackageReference` |
| 新增包体 | 0 |
| 新增内存 | 实测约 1.9 MB（5000 条），相比 SQLite 的 12.0 MB |
| 合规影响 | 无新增第三方组件，AC-10 维持现状 |
| 主要风险 | 不是存储，是 `FileIdBothDirectoryInfo` 枚举层（1–2 天，可单独验证） |

需要同步修订的文档：

- `docs/requirements.md` FR-4.2.1「本地 SQLite 单文件存储」→ 改为「本地单文件追加日志（JSONL）」
- `docs/m2-plan.md` P4 的"先定 SQLite"决策点 → 改为"存储引擎已复核，走文件方案；风险在 FileId 枚举层"

## 8. 已拍板（2026-11-08）

1. **标签数上限 = 50000。** 低于它全内存；达到上限后**显式拒绝新增**并在状态栏提示，
   不静默丢弃、也不自动清理旧记录。超限后自动切到"按目录分片文件"的方案否决：
   它会引入第二套读写路径，两套路径的行为差异会在半年后变成难查的 bug。

2. **跨卷失效的明示方式 = 状态栏一次性提示 + 虚拟节点留 7 天。**
   移动后标签丢失时，状态栏给一次性提示「N 个项目的标签因跨卷移动已失效」；
   同时在导航栏的「已失效标签」虚拟节点里保留这批记录 7 天，之后清理。
   不做模糊重绑（按文件名 + 大小猜回原文件）——猜错比丢失更难解释。

   两条一起构成 FR-4.2「跨卷移动丢失，需明示」的落地口径。

## 9. 已落地（2026-11-09）

实现位置：`Core/Tagging/TagStore.cs`（JSONL + 内存字典）、`Core/FileSystem/FileIdEnumerator.cs`（枚举层）、
`App/Views/PaneView.Tags.cs`（右键菜单）、`App/Views/MainWindow.Tags.cs`（懒加载与补标记）。

两处与原方案不同的口径，理由见 `m2-plan.md` §4.5 的落地口径：

1. **FileId 枚举从"按目录按需"改为"库非空即整条走"。** 原计划怕它慢，实测它比现有枚举还快一倍；
   而"按目录判断"会让同卷移动到无标签目录的文件当场丢标记，与 FR-4.2 的承诺冲突。
2. **FileId 为 0 时拒绝写入**并在状态栏说明。否则所有条目共用 `(卷, 0)`，给一个文件打标签
   会变成整目录变色——这是最容易被当成"标签库坏了"的一类 bug。

未落地的仍是需求里的 P1/P2 项：多色显示（4.1.2）、导航栏「标签」节点（4.1.5）、颜色自定义名称（4.1.7）、
清理失效项（4.2.6）、导入导出（4.2.7）、模糊重绑（4.2.9）。
