## 一、结论摘要

1. **原生崩溃已闭环。** 从 11-14 首次崩溃到 11-16，共抓到 6 份全内存转储，全部崩在同一帧
   `dui70.dll+0x65642`（`mov [rdx], rax`，`rdx = 0`）。根因是删除走 `SHFileOperation` 时
   缺 `FOF_SILENT`，Shell 在本进程内建 DirectUI 进度界面，与 TSF 输入上下文在窗口建/毁时互踩。
   加 `FOF_SILENT` 后，8 小时跑满 0 崩溃 0 转储，GDI 全程 183–191（崩溃轮同点位 641）。
2. **8 小时轮仍未判通过，但败因已更换两次，且都已定位修复。** 11-16 那轮败在托管异常
   （197 条，提示链路第 20 分钟起静默失效）；11-17 复跑该缺陷消失（0 条），但暴露出
   **提交内存随目录条目数快速上升、消息泵出现秒级停顿**——本轮因测试脚本把目录撑到 7.7 万项，
   属于被测场景失控，不能直接判为应用缺陷，但确有一条独立于条目数的慢增长（约 25 MB/h）需要定界。
3. **当前不具备勾掉 AC-03 的条件。** 缺一轮"目录规模受控 + 0 崩溃 + 0 托管异常 + 内存平稳"
   的 8 小时。建议先修一处脚本缺陷（copy 不收敛），再做一次受控 8 小时。

## 三、已定位并修复的问题

### P0-1 原生崩溃：Shell 删除进度界面（已闭环）

**证据链（四路独立，互相印证）**

| 证据 | 内容 |
|---|---|
| 转储 | 6 份逐帧一致：`dui70+0x65642`，写 `0x0`，栈 `dui70 → duser → msctf → shell32 → textinputframework` |
| 线程 | 崩溃线程不是 UI 线程（UI 线程 CPU 25 s 那条未被卷入） |
| 窗口快照 | 崩溃前抓到 `#32770` 系统对话框，标题"这将取消所有正在进行的传输。" |
| 资源台阶 | 同一点 GDI 196 → 641、提交内存 170 → 338 MB |

**根因**：`FileOperations.DeleteAsync` 为删除单开 STA 线程（`Jianlan.Delete`）且**没有消息泵**，
`fFlags` 缺 `FOF_SILENT`。Shell 按"要显示进度"准备，在本进程建 DirectUI 进度窗，靠窗口消息推进；
线程不泵消息，TSF 又给新窗挂输入上下文，两条线在窗口建/毁时互踩。

**修法**：`fFlags` 加 `FOF_SILENT`。不再要那扇窗，也就不需要消息泵、不给 TSF 添附着点。

**验证**：8 小时 0 崩溃、0 转储；GDI 全程 183–191 无台阶；三份独立短轮（21 / 22 / 30 分钟）全部越过旧崩点。

**代价**：批量删除没有 Shell 进度条。删除是瞬时操作，界面已有"正在删除"状态，可接受。

### P0-2 常驻模态窗被外部关闭后永久失效（已闭环）

**现象**：11-16 8 小时轮 197 条异常中 189 条为
`InvalidOperationException: 关闭窗口后，无法设置可见性`，栈顶恒为
`ModalSession.Run → ConfirmWindow.Notify → PaneView.ShowProperties`。

**影响**：从第 20 分钟起，**每一次**弹窗调用都抛，一次都没成功。窗口快照佐证——确认窗
（标题 `Delete`）在 3.3 / 8.2 / 18.6 / **20.2** 分钟各出现一次，之后 7.5 小时再未出现。
属性面板、删除确认、覆盖确认全部静默失效（异常被 `CrashLogger` 吞掉，用户只看到"点了没反应"）。

**根因**：`ModalSession` 只在"某一轮模态进行中"订阅 `Closing`，一轮结束即摘除，窗口隐藏期间
**无任何守卫**；此时收到 `WM_CLOSE`，WPF 直接销毁 HWND，`Show()` 从此必抛，单例又不重建。
`WM_CLOSE` 的来源是一条竞态：驱动以 `IsWindowVisible` 为判据发 `WM_CLOSE`，而 `Esc` 走
`SendInput` 是异步投递，消息泵被堵时 300 ms 内尚未处理完，于是 `Esc` 先到（隐藏 + 摘守卫）、
`WM_CLOSE` 后到（无人拦 → 销毁）。

**修法**：两个常驻窗构造时挂**永不摘除**的 `Closing` 守卫（仅主窗不可见时放行）；`Closed` 时
置空单例，下次重建；`ModalSession` 只负责结束本轮模态；驱动只对 `#32770` 发 `WM_CLOSE`。

**验证**：新增探针 `probe_singleton.py` PASS；`probe_modal.py` 四项 PASS；
21 分钟轮 `crash.log` 0 字节；11-17 复跑 149 分钟 0 条异常，确认窗 `4262900` 被反复叫出 10 次
始终是同一个 HWND。

### P1-1 驱动判据缺陷（已修，属测试方法问题）

| 缺陷 | 后果 |
|---|---|
| 收窗带 `h >= 300` 尺寸门槛 | 440×150 的确认框永远查不到，主窗被禁用到超时 |
| 只在批次末尾收一次窗 | 批次中间弹出的模态框导致整批动作打空 |
| 崩溃判据只看退出码与 `crash.log` | `procdump` 附着时进程被挂起，`poll()` 为 `None`，崩溃被记成"自退"或"无响应" |
| 未捕获异常 traceback 丢失 | 计划任务无控制台，脚本自身出错只留一个 `exit=1` |
| 汇总只说"crash.log 新增 N 字节" | FAIL 时看不出败因，需人工翻 400 KB 日志 |

现已改为：转储新增 `.dmp` 即判崩；批次起步先收窗；收窗范围含 `#32770` 且不再碰应用自身窗口；
异常按首行聚合进 `crashLogTypes`；traceback 落 `tools/ac03/last_error.log`。

### P1-2 去抖定时器在视图模型摘除后仍触发（已修）

11-16 轮另一类 9 次异常：`InvalidOperationException: PaneView 尚未附加视图模型`，
栈顶 `OnDebounceElapsed`。400 ms 的 `DispatcherTimer` 与"切换/关闭标签"存在一拍错位。
已在 `OnDebounceElapsed` 与 `QueueRefresh` 加 `_viewModel` / `_paneClosed` 守卫。

## 四、尚未解决 / 需要定界的问题

### U-1 提交内存持续上升（未定界，最需要结论）

两组数据指向**两种不同成因**，必须分开处理：

| 场景 | 现象 | 判断 |
|---|---|---|
| 11-16 轮，目录 1080 项恒定 | 提交 135 → 332 MB，约 **+25 MB/h**，工作集平稳 190–260 MB | 与条目数无关的**慢增长**，性质待定 |
| 11-17 轮，目录 2160 → 77287 项 | 提交 134 → 987 MB，工作集 215 → 620 MB 后回落至 90 MB | 与**条目数同步**，GC 后回落，更像"堆已提交未归还" |

已排除的方向：图标缓存按**扩展名/图标序号**去重，条目数再多也是有限键；
缩略图缓存容量上限 16；`PreviewHandlerRegistry` 按扩展名缓存。即**没有按路径无界累积的缓存**。
更可能是 `FileEntry` 视图模型数量、`FileSystemWatcher` 事件队列、以及大对象堆碎片共同作用。

**判定影响**：当前门槛只约束 GDI（<2000）与句柄（<10%），**没有内存门槛**。这是判定口径的缺口：
一个 8 小时会话涨到 1 GB 提交内存，用户机器上是能感觉到的。

### U-2 大目录下消息泵出现秒级停顿（待复现）

11-17 轮共 7 次"消息泵连续 3 秒无响应"，发生点与提交内存同步抬升：357 → 509 → 653 → 797 → 923 → 987 MB。
对照 11-16 轮（目录恒定 1080 项）**0 次**。倾向判断：目录 5–7 万项时的列表构建/刷新阻塞 UI 线程，
与内存压力叠加。**需要在受控目录规模下单独复现**，否则无法区分"应用性能问题"和"脚本把场景撑爆"。

### U-3 焦点复位率 12%（未收敛）

11-16 轮 69 次 / 571 批（12%）；11-17 轮 6 次 / 149 分钟；单轮 21 分钟曾低到 1 次。
含义：约一成批次在 `Esc`/模态/拖选后键盘焦点丢失，后续按键打空，靠自愈复位才继续。
动作落地指标（`actionsEffective`）仍为 true（mtime 有变化），**真实覆盖率被打折**。
8 小时内无恶化趋势（每小时 5–13 次，平稳），不阻塞验收，但应单独定位。

### U-4 删除失败 4 次（待核实）

11-17 轮 `app.log` 出现 4 条 `fs.delete code=E1007 msg="shell=0x50 · <路径>"`，
均为带多层 `(2) (3)` 后缀的深层文件名。`0x50` 对应的 `SHFileOperation` 语义【待核实】，
可能是"源被占用"或"路径过长"。测试产生这类病态文件名本身是脚本副作用，但**删除失败没有反馈给用户**
这一点值得确认。

### U-5 沙箱目录无界增长（脚本缺陷，非应用问题）

`act_copy_paste` 的"复制 → 粘贴 → 撤销"三步中，撤销在某些路径下未生效（或粘贴落在子目录，
撤销目标不匹配），导致条目数从 2160 指数式涨到 77287。连带污染三项指标：提交内存、
消息泵停顿、以及 `sandboxFileSpan`（1388）。**这是 11-17 轮不能用于判定的直接原因。**

## 五、判定口径的缺口

现有 PASS 条件为：无崩溃 + `crash.log` 无新增 + 句柄增长 <10% + GDI <2000 + 动作落地。
经过三轮 8 小时，发现三处覆盖不到：

1. **弹窗成功率没有指标。** 11-16 轮弹窗全线失效，`actionsEffective` 仍为 true——因为属性弹窗不写盘。
   目前只能靠 `crash.log` 反推。建议加 `dialogShown` / `dialogFailed` 计数（驱动侧即可实现）。
2. **没有内存门槛。** 建议增设"提交内存末点 ≤ 基线 × 2 或 ≤ 600 MB"一类的软门槛，
   至少要在报告里单列趋势，不能只看 GDI 与句柄。
3. **`crash.log` 只判有无、不判类型。** 一条噪声异常与"整条功能链路失效"在旧口径里等价。
   已加 `crashLogTypes` 聚合，后续应据此分级：**功能级异常（提示链路、导航、文件操作）直接 FAIL；
   可忽略级（第三方或已兜底的降级路径）计入报告不判 FAIL**。

## 六、建议方案（按优先级）

### 第一步：修脚本，让场景可控（必做，成本最低）

- `act_copy_paste` 的撤销改为"按粘贴目标名定向删除"，并在每轮批次后校验 `sandboxFiles`
  是否回到基线 ±10%，超出即重建沙箱（`prepare_work(force=True)`）。
- 沙箱每轮起跑前强制重置到 1080 项，避免上一轮残留污染（11-17 轮起点就是 2160）。
- 收益：下一轮 8 小时的目录规模恒定，U-1/U-2 才有可比性。**这一步不做，再跑 8 小时也是白跑。**

### 第二步：受控 8 小时，一次拿两个结论（推荐）

用修好的脚本跑 8 小时，同时回答两件事：

1. AC-03 是否通过（0 崩溃 + 0 功能级异常 + GDI/句柄达标）；
2. 提交内存的慢增长是 25 MB/h 还是更高（目录恒定，排除条目数干扰）。

- 成本：8 小时挂机，人工约 20 分钟看结果。
- 若内存仍线性上升且末点超过 600 MB，转第三步。

### 第三步：内存定界（条件触发）

- 用 `dotnet-counters` 或 `dotnet-gcdump` 在 2 小时处取一次堆快照，对比 6 小时处，
  按类型排序看增长源（`FileEntry` 实例数、`DispatcherTimer`、事件订阅、`FileSystemWatcher` 残留）。
- 成本约半天；只有在第二步确认"目录恒定仍涨"后才值得做。

### 第四步：大目录性能（独立于 AC-03，可并行）

- 用固定 5 万项目录做一次 30 分钟压测，观察消息泵停顿与内存，定位列表虚拟化的边界。
- 若确认是虚拟化未生效或每项开销过大，属独立性能工单，不阻塞 1.0。

### 不建议的做法

- **不建议再直接盲跑 8 小时。** 前两轮已经证明：不控目录规模、不看异常类型的长跑，
  跑完仍然只能得到"又发现有别的问题"的结论。
- **不建议为了过验收而放宽 `crash.log` 判据。** 11-16 轮那 189 条异常正是靠这条判据抓出来的；
  该做的是**分级**（功能级 vs 可忽略级），不是取消。
