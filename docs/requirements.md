## 1. 项目概述

### 1.1 定位

一款**轻量、原生、启动即用**的 Windows 文件资源管理器，替代系统 Explorer 的日常文件浏览与整理场景。

不追求功能大而全，追求**打开快、不卡顿、不崩溃**。

### 1.2 核心矛盾与取舍原则

功能越多 → 启动加载越多 → 启动越慢。

因此确立**唯一最高优先级约束**：

> **任何功能，如果使冷启动时间增加超过 50ms，或引入无法兜底的崩溃点，则该功能不进当前版本。**

这条约束用于裁决所有功能取舍，优先级高于"用户要求"和"竞品都有"。

### 1.3 参考对象说明

需求描述中的 "Files" 指开源项目 **files-community/Files**。该项目技术栈为 WinUI 3 + .NET，实测冷启动约 **1.5–3.0 秒**。

**结论：参考其功能清单与交互，不参考其架构与技术基线。** 本项目选用 WPF 正是为规避该问题（理由见 §9.1）。

### 1.4 性能基线参考

| 产品 | 技术栈 | 冷启动（SSD 参考值） | 常驻内存 |
|---|---|---|---|
| Windows 11 资源管理器 | C++ / WinUI 混合 | 400–800ms（进程预热后 <300ms） | 80–150MB |
| files-community/Files | WinUI 3 + .NET | 1500–3000ms | 200–400MB |
| Everything | C++ / Win32 | <150ms | 20–40MB |
| **本项目** | C# / .NET 9 / WPF | **P50 ≤700ms，P95 ≤900ms（实测约 605ms）** | **≤120MB（见 NF-05 分档）** |

> 竞品数据为公开量级参考。本项目数值为 M0 同机实测，方法见 `docs/performance-gate.md`。

## 2. 术语

| 术语 | 说明 |
|---|---|
| 冷启动 | 进程创建 → 主窗口首帧可交互的耗时，不含系统文件缓存预热 |
| 虚拟化 | 仅渲染可视区域内的列表项，与项目总数解耦 |
| Shell | Windows 外壳组件，提供图标、右键菜单、属性页、预览等服务 |
| Known Folder | 系统已知文件夹（桌面/文档/下载等），由 `SHGetKnownFolderPath` 获取 |
| File ID | 卷内文件唯一标识（VolumeSerialNumber + FileIndex），重命名/移动后不变 |
| Preview Handler | Windows Shell 预览处理程序，COM 接口 `IPreviewHandler` |
| 性能预算 | 某功能允许消耗的启动耗时/内存额度，超出即降级 |
| STA 线程 | 单线程套间，COM 组件（含预览处理程序）必须在 STA 线程创建与调用 |

## 4. 设计原则

| 编号 | 原则 | 可验证的落地方式 |
|---|---|---|
| P1 | 首帧优先 | 窗口绘制完成前，禁止任何磁盘 IO、网络请求、Shell COM 调用、数据库打开 |
| P2 | 一切延迟 | 图标、缩略图、右键菜单、标签数据库、会话恢复、预览均在首帧后异步加载 |
| P3 | 单进程单窗口模型 | 不使用多进程架构，不做浏览器内核渲染 |
| P4 | 零常驻 | 无常驻后台服务、无开机自启、无托盘进程、无全盘文件监控 |
| P5 | 失败不崩溃 | 一切外部调用（Shell、磁盘、注册表、COM）必须有异常兜底与降级路径 |
| P6 | 可裁剪 | 功能模块独立初始化，未使用的模块不进入内存 |
| P7 | 不接管系统 | 不修改默认打开方式、不注入 Explorer、不改文件关联（D5） |

## 5. 性能与稳定性指标

> 本章是验收底线。任何功能验收前，这 11 项必须同时达标。

| 编号 | 指标 | 目标值 | 测量方法 |
|---|---|---|---|
| NF-01 | 冷启动（进程启动 → 窗口可交互） | P50 ≤700ms，P95 ≤900ms | 见 `docs/performance-gate.md`；20 次取分布，Release + ReadyToRun |
| NF-02 | 热启动（退出后立即重启） | ≤500ms | 同上 |
| NF-03 | 打开含 10000 个项目的目录 | ≤800ms 显示首批内容，UI 线程无 >100ms 阻塞 | 构造测试目录 + 启动埋点 |
| NF-04 | 列表滚动帧率 | ≥55fps（10000 项目录） | `CompositionTarget.Rendering` 采样 |
| NF-05 | 常驻内存（10000 项目录，浏览 10 分钟） | **分档：** 单窗格 ≤120MB；双窗格 ≤150MB；开启预览窗格 ≤190MB | 任务管理器 / Process Explorer 工作集 |
| NF-06 | 稳定性（8 小时连续操作） | 0 崩溃、0 未处理异常；句柄增长 <10%，GDI 对象 <2000 | 脚本化压力测试 |
| NF-07 | 安装包体积 | ≤30MB（框架依赖）；自包含 ≤80MB | 发布产物 |
| NF-08 | 启动回归门禁 | 每次发布前实测 P50/P95 并附于 README；CI 只做启动冒烟 | `tools/startup-bench` + 人工判定 |
| NF-09 | 单次文件操作不得阻塞 UI | UI 线程阻塞 <16ms | 后台执行 + 进度反馈 |
| NF-10 | 长路径支持 | 支持 >260 字符路径（`\\?\` 前缀），不崩溃 | 构造 300 字符路径用例 |
| NF-11 | 错误提示友好 | 权限不足/文件占用/路径不存在等须给可理解提示，不弹原始异常 | 手工用例 |

**补充约束：**

- NF-12：预览窗格单次渲染超时 2s 必须降级显示"无法预览"，不得卡住 UI。
- NF-13：任何 COM 对象使用后必须释放，CI 中加入句柄/GDI 泄漏检测用例。

#### FR-4.2 存储与跟踪方案

| 方案 | 说明 | 评估 | 结论 |
|---|---|---|---|
| A. NTFS 备用数据流（ADS） | 写入 `file.txt:tag` | 复制/上传/压缩丢失，跨盘与网络不支持，部分安全软件告警 | ❌ |

| D. Shell 属性系统（`System.Keywords`） | 写 Windows 文件属性 | 写入慢、格式兼容差、可能触发云同步 | ❌ |

| FONT-02 | 字体名按当前界面语言取本地化名（`FontFamily.FamilyNames` 取 `zh-cn`，缺失时回落 `en-us`），避免中文系统显示为 "Microsoft YaHei" 这类英文名 |
| FONT-03 | 配置中保存的字体在启动时若不存在（换机器、卸载字体），**自动回落默认字体且不报错**，同时在设置页标注"原字体不可用" |
| FONT-04 | 字体与字号通过全局 `DynamicResource` 下发，切换时只更新资源，不重建视图 |
| FONT-05 | 字号变更后须重新计算列表行高与虚拟化项尺寸，滚动位置按项目索引恢复，不得跳回顶部 |
| FONT-06 | 字号 >16pt 时，列表列宽按内容自适应扩展，避免文字截断；图标尺寸不跟随字号变化 |
| FONT-07 | 高 DPI（125%/150%/200%）下字体渲染清晰，不做位图缩放 |
| FONT-08 | 字体切换必须在 100ms 内完成；若某字体加载超时（>500ms），保持原字体并提示 |
| FONT-09 | 不支持字体平滑、字重、字间距等高级排版选项（第一版范围外） |
| FONT-10 | **程序不打包、不内置、不随包分发任何字体文件**，全部使用系统已装字体。理由：避免字体许可合规风险与包体膨胀；缺失字体一律回落系统默认字体 |

| C12 | 接管系统"打开文件夹"默认行为 | 注册表劫持，卸载残留风险（D5 已决议第一版不做） |
| C13 | 巨型单文件打包 / 全量资源内嵌 | 影响 NF-07 与加载效率 |

**决策记录（ADR-001）：** 若后续有强需求要求 C 档功能，唯一可行路径是"独立可选组件、默认不安装、独立进程运行"，绝不并入主进程。

## 9. 技术方案

### 9.1 技术栈（已确认）

**C# + .NET 9 + WPF，ReadyToRun 发布。**

选择理由：

| 维度 | WPF | WinUI 3 | Tauri | WinForms |
|---|---|---|---|---|
| 冷启动（实测基线） | ~600ms | 800–1500ms | 400–700ms | 100–200ms |
| Shell 互操作（图标/右键菜单/属性页/预览） | 成熟完善 | 一般，需 Win32 兜底 | 几乎为零，需 unsafe 绑定 | 成熟 |
| 列表虚拟化 | 内置 | 内置 | 需自建 | `VirtualMode` |
| 深色 + 高对比度 | 原生 | 原生 | 易（CSS） | 需全量自绘 |
| 失败模式 | 少见 | API 版本碎片化 | 易混淆 v1/v2，Rust 借用检查难修 | 少见 |

**核心判断：** 文件管理器约 90% 的工程难度集中在 Windows Shell 互操作，这恰好是 WPF 资料最厚、跨平台方案最薄的位置。选 WPF 的首要理由不是"快"，而是"能把稳定性做达标"——实测代价是启动基线高于 WinForms 约 350ms。

**不选 WinUI 3：** MUX 控件库初始化 + WinRT 激活导致冷启动基线 800ms 以上，且深色主题与 WPF 同样成熟但生态资料显著更少。参考对象 Files 启动慢正源于此。

**不选 WinForms：** 启动更快且虚拟化成熟，但深色模式与高对比度需全量自绘控件，工作量不亚于重写 UI 层，与 FR-5.1.1/FR-5.1.2 冲突。

**降级路径：** 若 M0 阶段 WPF 冷启动无法压到 600ms 以内，将"目录枚举 + 图标提取"两个热点用 C++ 写成独立 DLL 局部替换，不更换 UI 框架。

**环境准备（开发机当前缺少）：**
- 安装 .NET 9 SDK（约 200MB）
- Windows 10 SDK（调用 Shell 与 Win32 API 需要）
- Visual Studio 2022 或 Rider（可选，命令行 + AI 编码亦可）

**框架基线（同机实测，Release + R2R，三次以上取值）**

| 方案 | 到窗口可交互 |
|---|---|
| WPF 最小空窗口（默认） | 1030–1120 ms |

### 9.3 目录枚举与列表性能

| ID | 要求 |
|---|---|
| T-01 | 枚举在后台线程执行，结果分批回调 UI（首批 ≤200 项立即渲染） |
| T-02 | 排序在后台线程完成，UI 只做视图索引映射 |
| T-03 | 大目录（>5000 项）自动进入"简化模式"：不预取图标、不生成缩略图 |
| T-04 | 目录刷新采用差异更新而非全量重建，保持滚动位置与选中状态 |
| T-05 | 不跟随符号链接/联接点递归，避免循环死锁 |
| T-06 | 列表模板使用轻量控件组合，避免嵌套面板；单元格内控件数 ≤3 |

### 9.4 稳定性要求

| ID | 要求 |
|---|---|
| S-01 | 三重全局异常捕获（`AppDomain` / `Dispatcher` / `TaskScheduler`），写日志，UI 提示后可继续运行 |
| S-02 | 所有 Shell COM 调用包 try/catch 并正确释放；优先用 `ComWrappers`/RCW 生命周期管理 |
| S-03 | 文件路径统一走封装 API，自动加 `\\?\` 长路径前缀 |
| S-04 | 网络位置/可移动设备/权限受限目录一律 3s 超时，超时降级提示 |
| S-05 | 后台任务统一 `CancellationToken`，目录切换时取消旧任务，防止结果污染 |
| S-06 | 设置写入用"临时文件 + 原子替换"，解析失败回落默认并备份损坏文件 |
| S-07 | 崩溃后下次启动提示"上次异常退出"，提供日志导出（FR-10.6） |
| S-08 | Preview Handler 调用前检查线程套间为 STA，调用后强制释放 |

## 11. 风险与对策

| 编号 | 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|---|
| R1 | 冷启动无法达标 | 核心目标失效 | 中 | M0 先验证；备选 Win32 宿主外壳混编，或热点改 C++ DLL |
| R2 | Shell 图标/右键菜单性能与稳定性 | 卡顿、崩溃 | 高 | 全异步 + 超时 + 缓存；右键菜单失败降级为自建精简菜单 |
| R3 | 预览窗格 Handler 崩溃或挂起 | 整个进程崩溃 | **高** | 独立 STA 线程 + 2s 超时 + 异常隔离；P2 阶段考虑独立进程渲染 |
| R4 | 双窗格 + 预览窗格内存超预算 | NF-05 超标 | 中 | 分档预算（120/150/190MB）；超预算自动降级预览 |
| R5 | 彩色标签 File ID 跨卷失效 | 用户感知丢数据 | 高 | 文档明示限制；同卷内提供模糊重绑（FR-4.2.9） |
| R6 | 大目录（10 万项）性能崩坏 | 体验崩塌 | 中 | 分批枚举 + 简化模式 + 上限告警 |
| R7 | 长路径/权限/占用文件导致异常弹窗 | 稳定性差评 | 高 | S-02~S-04 全覆盖；错误提示统一封装 |
| R8 | 功能追加导致启动退化 | 目标逐步失守 | **高** | NF-08 启动门禁进 CI，超预算构建直接失败（唯一制度性防线） |
| R9 | 范围膨胀导致无法交付 | 项目停滞 | 高 | §8.3 黑名单硬性执行；新增需求须过 §1.2 裁决 |
| R10 | 开发者不熟悉 C#/WPF，AI 生成代码难以调试 | 效率下降 | 中 | 严格分层（Core 与 UI 解耦）、关键路径写单元测试、复用成熟开源实现参考 |
