## 三、P1：地基——从「窗口即浏览器」拆成「窗口壳 + 窗格」

### 3.1 为什么这是瓶颈

| 现状 | 数字 |
|---|---|
| `MainWindow.xaml.cs` | 962 行 |
| `MainWindow.FileOps.cs` / `.DragDrop.cs` / `.Watcher.cs` / `.Icons.cs` / `.PerfProbe.cs` | 299 / 168 / 129 / 54 / 434 行 |
| `MainViewModel.cs` | 514 行 |

这些文件全部建立在同一个前提上：**一个窗口 = 一个浏览区**。列表控件叫 `FileList`、状态栏只有一个、`FileSystemWatcher` 挂在窗口上、命令处理器直接操作窗口字段。

多标签、双窗格、收藏拖入、主页卡片点击全都要问同一个问题："这个操作作用于哪个浏览区？"——没有"浏览区"这个实体，每一项都要在窗口里再写一份 if。

### 3.2 目标结构

```
MainWindow（壳：只管布局、命令路由、窗口状态）
├── TabStrip                  ← FR-2，顶部，ItemsControl + 横向滚动
├── PaneHost                   ← 1 个或 2 个 PaneView
│    └── PaneView (UserControl)   ← 从 MainWindow 拆出的浏览区
│         ├── 面包屑 / 地址栏
│         ├── FileList（虚拟化三件套）
│         └── 状态栏（每窗格一份）
├── NavPane（窗口级，作用于 FocusedPane）
└── ContextMenu 宿主
```

对应 ViewModel：

| 类型 | 职责 |
|---|---|
| `PaneViewModel` | 现 `MainViewModel` 改名，保留导航/枚举/排序/选中/状态栏/文件大小字典。**去掉**窗口级成员（打开设置、关窗、窗口尺寸） |
| `TabItemViewModel` | `{ PaneViewModel Pane, string Title, IconKey, bool Pinned }`，标题随 pane 路径变化 |
| `ShellViewModel`（或直接留在 MainWindow） | `ObservableCollection<TabItemViewModel> Tabs`、`ActivePane`、`FocusedPane`、双窗格开关 |

### 3.3 四步迁移（每步都要求行为零变化）

| 步 | 动作 | 验收 | 工作量 |
|---|---|---|---|
| S1 | **机械抽取** `PaneView`：把 `MainWindow.xaml` 里 `Grid.Row=1` 的浏览区与状态栏整块剪到 `PaneView.xaml`，`DataContext` 仍是原来的 `MainViewModel`；`MainWindow` 用一个 `<local:PaneView/>` 托管 | 外观与交互零差异；119 单测通过；AC-05 边界场景重跑 | 1 天 |
| S2 | **改名与焦点**：`MainViewModel` → `PaneViewModel`；`MainWindow` 持有 `Panes` + `ActivePane`；所有命令从 `_viewModel.X` 改为 `ActivePane.X` | 仍只有一个 pane，行为不变 | 1 天 |
| S3 | **标签栏与视图复用**：`TabStrip` 绑 `Tabs`；`ContentControl Content="{Binding ActivePane}"` + `DataTemplate` → `PaneView` | 多标签可切换、可关闭；切回时滚动位置与选中还原 | 1 天 |
| S4 | **双窗格**：`PaneHost` 换成两列（或两行）`Grid` + `GridSplitter`；点击决定 `FocusedPane`，焦点窗格画强调色描边 | F3 开关；两侧路径/历史互不影响；跨窗格拖放 | 0.5 天 |

S1 是纯搬运，**不要在这一步顺手改逻辑**。搬运 + 改名分开做，出问题时能立刻判断是"搬错了"还是"改名改错了"。

### 3.4 视图复用与内存

需求 FR-2 要求"按需加载 + 视图复用"，且单标签壳 ≤3MB、双窗格增量 ≤30MB。策略：

- **ViewModel 全保活，View 只保活动那一份。** 非活动标签保留目录、排序、选中项路径、滚动偏移；切走时 `ContentControl.Content` 换掉，`PaneView` 被回收。
- 如果实测切换耗时 >50ms（FR-2.1 的指标），再加"最近 1 个视图"的 LRU 缓存；不要一上来就保活 20 个视图——每个 `PaneView` 带一个虚拟化 `ListBox` + 图标缓存引用，20 份稳超预算。
- 切回时的还原顺序：先设目录 → 枚举 → 恢复排序 → 按路径恢复选中 → 恢复滚动偏移。前两步已有（`NavigateAsync`），后三步是把现有 `RefreshAndSelectAsync` 的收尾逻辑参数化。

### 3.5 监听器与焦点

`FileSystemWatcher` 现在是每窗口一个。多标签后：

- **只有 `ActivePane` 的 watcher 在跑**，切走即停。需求 FR-2 的"非活动标签仅在激活时校验目录是否变更"就是这个意思。
- 切回时用一次轻量枚举比对（mtime + 条目数）判断是否需要重建，避免"切回来发现是旧内容"。
- 双窗格时两个 pane 各自一个，但**非焦点窗格的 watcher 降为 2 秒节流**（需求 FR-3 要求非焦点窗格降优先级）。

### 3.6 本轮走查暴露的两个隐性债，必须在 P1 一并处理

| 债 | 说明 |
|---|---|
| `FocusVisualStyle="{x:Null}"` | `Row.Item`、`Button.Toolbar`、`Nav.Item` 等样式里被显式置空。键盘走查时看不到焦点在哪，直接卡住 FR-10.7 / AC-08。改法是给列表行与按钮各做一条焦点态（描边或底色），而不是把 `Null` 删掉走 WPF 默认虚线框——深色主题下默认框几乎不可见 |
| 列表行模板元素数 ≤3 的约束 | 彩色标签要在文件名前加圆点，会变成 4 个元素。要么把图标与圆点合成一个 `Grid`（仍算 1 个），要么在 `ui-guidelines.md` §14 记录一次例外。**先试合成**，它同时解决图标位置微调 |

- 拖拽排序用 `DragDrop.DoDragDrop` + 插入位置竖线。**不要**复用列头那个 `Thumb` 方案——列头是连续调整宽度，标签是离散重排，语义不同。

### 4.3 FR-7 收藏（2 天，已落地）

- 存储：`settings.json` 新增 `bookmarks` 数组（上限 500，FR-7.9）。字段：`{ path, name, kind(folder|file), group, icon, color, addedAt }`。按需求决策不新建数据库。
- **分组名即身份**：分组不额外发 Guid。`settings.json` 是用户会打开看甚至手改的文件，多一层 `id → name` 映射只会让手改更难。上限 50 组；删组时条目落回"未分组"而不是跟着消失。
- 入口：导航栏收藏区 + `Ctrl+D` + 从列表拖入（FR-7.4）。导航栏是**一条扁平 `ObservableCollection<INavRow>`**（系统节点 / 分区标题 / 空态 / 分组 / 收藏项共处一条），按类型挑 `DataTemplate`。不用"快速访问 + 收藏两棵树"：两棵树就是两套选中态，点了收藏那边还亮着，得再写一处手动互斥。`NavItem` 是 `record`、改不成基类，只能靠接口与收藏行共用一条列表。
- 拖拽排序（FR-7.6）：插入指示复用标签排序那条线。算目标序号时**要先把被拖项从同组邻居里滤掉**，否则往下拖会差一位（被拖项自己还占着原来那个位置）。
- 外观预设（FR-7.5）：固定六色 + 六个图标，不给取色器/图标浏览器——任意颜色会在深色下读不出来，开放字形码位等于把字体细节泄露给用户。色值进 `settings.json` 走 `#RRGGBB`。
- 失效检测（FR-7.7）：导航栏渲染后异步**整批**检测（`Task.WhenAny(probe, Task.Delay(3s))`，超时保留上次结果），失效项灰色；批量清理走右键菜单。**不要在渲染前同步检查**——UNC 路径会让导航栏首帧卡住。
- 与 FR-1.2.5 / FR-1.1.5 同源：主页的收藏区直接读同一个集合。

**两条 WPF 坑（走查时才暴露，改模板/菜单时先看这里）**：

1. 自定义 `MenuItem` 模板若不给子菜单留 `Popup`（名字必须是 `PART_Popup`、`IsOpen` 绑 `IsSubmenuOpen`），带 `ItemsSource` 的菜单项**永远展不开**——菜单照常弹出、文字照常显示，只是子菜单一片空白，没有任何异常。`Role` 触发器同时用来出右侧箭头。
2. `ItemsSource` 生成的容器只被塞 `Header`/`HeaderTemplate`，**不设 `DataContext`**；容器的 `DataContext` 是从父菜单继承下来的（在这里就是收藏行）。所以"子项点的是哪个预设"要读 `MenuItem.Header`，"这条菜单属于哪一行"要读父菜单的 `DataContext`。

### 4.4 FR-8 工作区（1.5 天，已落地）

- 独立 `workspaces.json`（`AppPaths.WorkspacesFile`）。需求明确"不参与冷启动默认路径"——放在 settings.json 里等于每次启动都解析一遍所有工作区的标签列表。**实际落地是懒加载**：首帧不读，由 `MainWindow.InitializeWorkspaces` 在首帧内容就绪后读一次，导航栏与主页再各补一段。唯一的例外是 FR-8.4 启动恢复，那是用户显式开启的路径。
- 结构 `{ schemaVersion, items: [{ name, savedAt, activeTabIndex, tabs: [{ path, second, pinned }] }] }`。**名字就是身份**，不发 Guid（同 §4.3 收藏分组的理由）。上限 50 个工作区、单工作区 50 标签；标签存 `second`（双窗格另一侧）与 `pinned`。
- 恢复：先建壳（`AddPending`）、再逐个就绪，与 FR-2.11 同一套异步策略。**先建新标签再整体替换旧标签**（`TabHostViewModel.ReplaceWith`）：逐个 `Close` 会把被替换的标签压进"最近关闭"栈，打开一次工作区之后 `Ctrl+Shift+T` 会一个个还回来，看起来像工作区没生效。
- 双窗格形态**由数据推出来**，不额外存 `splitEnabled`：工作区里只要有一个标签记着 `second`，存的时候就是分屏的。存两份必然出现"开关说分屏、标签都没有第二窗格"这种自相矛盾的状态。
- FR-8.4 与 FR-2.11 互斥：设了 `behavior.startupWorkspace` 就由 `AppSettings.Normalize` 把 `restoreLastSession` 置 false（显式选择胜过默认值）。0.2.0 的设置页还没有会话恢复开关（属 FR-5.2.9），所以"另一个置灰"等那一项落地时一起做；改工作区的入口在导航栏/主页的工作区行右键菜单里。
- 没有单独的"管理工作区"窗口：列表在导航栏与主页各一份，标签数与最后保存时间显示在行上（标题 + 悬停提示），重命名/覆盖/删除走右键菜单。再开一个窗口只会让同一份数据多一处要同步的地方。

### 4.5 FR-4 彩色标签（4 天，P0 + 4.1.5 已落地 2026-11-09）

**决策已定（2026-11-05）：不引入 SQLite，走单文件追加日志 + 内存索引。**
完整论证见 [`docs/tags-storage.md`](tags-storage.md)，要点：

| 指标（5000 条实测） | SQLite | 文件 + 字典 |
|---|---|---|
| 私有提交增量 | +11.96 MB（释放连接后不归还） | +1.90 MB |
| 4 万次可视区查询 | 189 ms | 200 万次 201 ms（快 47 倍） |
| 包体 | +1.4 MB（`e_sqlite3.dll`） | 0 |
| 新增依赖 | 2 个包 | 0 |

NF-05R 只剩 20 MB 余量，而 SQLite 一口气要 12 MB 且不退——在"零依赖 + 内存紧张 + 包体只剩 5MB"三条约束下，它换来的只是"更正规"的心理收益。

**真正的风险不在存储，在 FileId 的获取。** `FileSystemEnumerable`（`FindFirstFileEx`）拿不到 FileIndex，
`WIN32_FIND_DATA` 里没有这个字段。必须改用 `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` 自己枚举。

> **2026-11-08 已 spike 验证通过**，见 [`docs/fileid-enumeration.md`](fileid-enumeration.md)。
> 结论：可行，且比现有实现更快（万项纯枚举 6.2 ms vs 11.7 ms，枚举+排序持平）。
> 五个必须做对的点已写成清单：`BY_HANDLE_FILE_INFORMATION` 的 FILETIME 对齐、会返回 `.`/`..`、
> 必须自带 `\\?\` 前缀且先 `GetFullPath`、卷序列号要单独取并目录内共用、无权限目录要降级。
> 工作量从"1–2 天风险项"降为 **0.5 天**，FR-4 的方案不需要改。
> 仍未验证的四项（ReFS/exFAT、真实远程 SMB、MFT 复用、冷缓存）都不挡开工，已列在该文档 §4。

**落地要点**

| 点 | 做法 |
|---|---|
| FileId 枚举 | `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)`，处理 `FILE_ID_BOTH_DIR_INFO` 结构、缓冲区不足重启、长路径、UNC。**落地时改了口径**：不再是"只在有标签的目录才走"，而是"标签库非空就整条走它"——理由见下面的落地口径第 1 条 |
| 存储 | `%LOCALAPPDATA%\Lingpane\data\tags.jsonl`，每行一条 `set`/`del` 操作；`Flush(true)` 落盘；行数 > 存活数×3 且 > 2000 时后台压缩 |
| 延迟加载 | 首次"设置标签"或"显示带标签目录"才读文件建索引；启动路径不碰（否则冷启动 +几十 ms） |
| 查询 | 内存字典 `Dictionary<(uint,ulong),TagRecord>`，可视区查询直接哈希，无批量/逐项之分 |
| 渲染 | 圆点放进**本来就有**的 12px 标签槽位（`Size.Tag.Gutter`），行模板元素数不变；无标签时整颗隐藏 |
| 上限 | 5 万条，超过拒绝新增并在状态栏提示（显式降级，不静默） |
| 跨卷失效 | 明确告知"跨盘移动后标记丢失"（需求已接受此限制），不做模糊重绑（那是 P2 需求） |

**落地口径（2026-11-09，`Core/FileSystem/FileId*`、`Core/Tagging/*`、`PaneView.Tags.cs`）**

1. **FileId 枚举从"按需"改为"库非空即整条走"。** 原计划是"只有该目录存在标签记录时才走这条路径"，
   落地时发现它换不来任何东西、还破坏需求：同卷把文件移到一个"没有标签记录"的目录后，
   按目录判断就不去取 FileId，标签当场不显示——而 FR-4.2 明确承诺"同卷移动后仍生效"。
   而"慢路径"这个前提本身是错的：spike 实测它比 `FileSystemEnumerable` 还快一倍
   （万项 6.2 ms vs 11.7 ms），双枚举才是真的贵。所以：**标签库非空 ⇒ 一次 FileId 枚举，
   不再枚举第二遍**；失败（无权限、卷不支持、网络盘）回落普通枚举，标签只是不显示。
2. **FileId 为 0 一律拒绝写入。** exFAT / 部分网络盘可能给不出稳定标识，全落成 `(卷, 0)`
   会让给一个文件打标签变成整目录变色——最难解释的一类 bug。状态栏显式提示"该位置不支持标签"。
3. **库就绪后补标记不重建列表**（FR-4.2.5）：只重取一次 FileId 再逐条 `SetTags`。
   重建会顺手丢掉文件夹大小结果与滚动位置。
4. **`tags.jsonl` 的 `del` 行不带 `c`/`t`**：这份文件用户会打开看，`"c":0,"t":0` 只是噪音。
5. **圆点颜色固定不跟主题**：配色写死在 `TagPalette.Hex`，"黑"在深色背景上靠 0.5px 描边救，
   而不是把它偷偷换成灰——用户点的是"黑"，换个颜色等于改了标记的含义。

**4.1.5 导航栏标签节点（2026-11-09 补，`ViewModels/TagResultsViewModel.cs`、`Views/TagResultsView.xaml`）**

6. **先分层，再挂节点。** 加「标签」之前先把四块的头做出来（位置 / 收藏 / 标签 / 工作区）：
   用户的反馈是"三块混在一起"，但根因不是功能重叠——四者语义各不相同，而是**界面没有声明每块是什么**。
   顶部七个系统节点原本没有标题，而「收藏」「工作区」的标题是 12px 三级灰、比条目还小，
   读起来像第八、第九个系统节点。所以：每块一个标题，标题用次级色 + 加粗 + 上方留白与一条分隔线；
   收藏项图标从文件夹换成星标，否则它和系统位置用同一个形状。主页单独置顶、不归任何一块——
   它不是一个"位置"，塞进「位置」下面会让那一块的第一项与其余七项不是同一类东西。
7. **结果页是一种标签形态**（`TabKind.TagResults`），不是虚拟目录、也不是弹窗。
   虚拟目录要伪造一个路径，而主窗格的导航栈、目录监听、地址栏全建立在"路径存在"上，
   为一份临时聚合去骗它们会把那些判断全部拖下水；弹窗则丢掉"跳走再回来"的语义。
   代价是它不参与会话恢复（`TabMarker` 对它给空串），这一条是明确的取舍而不是遗漏。
8. **只列用过的颜色**：八个全摆出来更像调色板，而这一块要回答的是"我标过哪些颜色的东西"。
   空库给一句「右键文件即可添加」的空态，与收藏区一致。
9. **结果页不显示修改时间**：那要对每条记录各发一次 IO，几千条在网络盘上足够让一次点击变成几秒空白；
   双击跳过去就能看到。

### 4.6 FR-9 预览窗格（4 天，风险最高）

- COM：`IPreviewHandler` 必须在**独立 STA 线程**创建与调用（FR-9.2.2）。项目里已有先例——`SHFileOperationW` 就在独立 STA 线程，直接照抄那套线程封装。
- 三条防线：2s 超时（`Task.WhenAny` + 释放）、`CancellationToken` 取消上一次、异常一律降级为"文件图标 + 基本信息"。
- 降级渲染：文本 ≤1MB 直接读；图片用 `BitmapImage` + `DecodePixelWidth`（**不要**解全图，50MB 的图会吃掉整档内存预算）；PDF/音视频只走 Preview Handler，失败就显示基本信息。
- 预算：预览窗格内存档位是 230MB，超预算自动降级为"仅文本 + 基本信息"（FR-9.2.7）。降级判断放在每次预览完成后，不是启动时。
- UNC 与可移动设备默认不自动预览（FR-9.2.8），要点击一次才触发。
- 关闭窗格立即释放 Handler 实例与文件句柄（FR-9.2.6）——这条最容易漏，因为窗格关闭时没人会想到还有 COM 持有文件。

### 4.6.1 FR-9 预览窗格落地口径（2026-11-09，主体）

**做了什么**：窗口右侧一栏，跟焦点窗格的选中项走。文本/位图内建渲染，其余类型走系统缩略图，
都不行就图标 + 基本信息。开关 `Alt+P`、宽度可拖可持久化、默认关闭。

| 点 | 做法 | 理由 |
|---|---|---|
| 一栏挂在哪 | 主窗口外层的第 4、5 列（分隔条 + 窗格），**不进** `PaneHost` 的 3×3 | 预览是窗口级的：分屏时两个窗格共用一个，`PaneHost` 里放就会变成"每边各一个预览"，语义错 |
| 开关与显示分开 | `_previewOpen`（意图）与 `ApplyPreviewLayout()`（此刻是否可见）分两个概念 | 主页/标签结果页没有选中项，那两种形态一律收起；把两者合成一个字段，切一次标签就得重新按一遍 `Alt+P` |
| 关掉时怎么收 | 宽度归零，控件与分隔条都留着（只改 `Visibility`） | 重建控件会把用户拖过的宽度与正在显示的内容一起丢掉 |
| 类型判定 | 按扩展名分 `Text` / `Image` / `Shell`，纯字符串判断、不碰磁盘 | 选中项高频变化，分类必须毫秒级；"是不是二进制"要读到内容才知道，那一步交给读取方 |
| `.svg` / `.webp` 不归图片 | 都丢给 Shell | SVG 用户要看的几乎总是图形本身；WPF 不带 WebP 解码器，当图片会在渲染阶段失败 |
| 防抖 + 票号 | 300ms `DispatcherTimer` + 每次请求 `_generation++` | 只靠 `CancellationToken` 不够：取消是协作式的，**已经算完的结果照样会回来**，会把新内容盖掉 |
| 图片限幅 | 先 `BitmapDecoder` 读头部尺寸，再决定限宽还是限高 | 只设 `DecodePixelWidth` 时，100×20000 的长条图在宽 512 下高会变成十万像素，一张图吃掉 200MB |
| 文本截断 | 文件读 1MB，**展示**最多 20 万字符 | 1MB 纯文本铺进 `TextBox` 要几百毫秒、十几 MB 托管堆，而用户只想确认"这是什么文件" |
| 二进制嗅探先认 BOM | UTF-16 的 BOM 命中就先当文本 | UTF-16 文本里全是 NUL，不先认 BOM 会把每个 `.txt` 都判成二进制 |
| 缩略图独立 STA 线程 | 照 `FileOperations.DeleteAsync` 那套封装，2s 超时后**不等**后台线程 | 第三方提供者可能一直不返回，强等等于把超时做成假的 |
| 内存预算按可核算量算 | 解码像素数 × 4 + 字符数 × 2，超 40MB 降级 | 进程工作集里混着框架与列表缓存，拿它当判据会让降级在别的模块吃内存时莫名触发 |
| UNC 先于 `DriveInfo` | 先判 `\\` 前缀，再问盘类型 | `DriveInfo` 对断线的映射盘会卡几十秒；UNC 先挡掉，走到 `DriveInfo` 的一定是本地盘 |
| 多选只在标题块说一次 | 标题写「已选中 N 项」、副标题写总大小，内容区留空 | 一开始内容区也画了一份，同一句话上下各一遍；"没有单个文件可看"自己就说明问题 |
| 图标按 32px 原生尺寸 | 新增 `ShellIconProvider.GetLarge`（`SHGFI_LARGEICON`），不与 16px 共用缓存 | 把 16px 列表图标放大到 48 得到一团没有轮廓的白块；两张表混用会让大图标也被缓存成 16px |

**未做（明确留白）**：`IPreviewHandler` 宿主。现在 PDF / Office / 音视频只出**缩略图**
（第一页、首帧），不能翻页、不能播放——FR-9.1.3 的"可播放"因此尚未满足。
这一块要 `IObjectWithSite` + `IPreviewHandlerFrame` + `HwndHost` 三件套，
且必须按"随时会崩"设计（独立 STA 已有，进程级隔离是 P2）。留给 P6 的第二批。

  第一张跑完 `showPreview` 已经是 true，第二张再"切换"就把它关掉了。
  工具改成"摆到指定状态"（先读 `_previewOpen`，不同才切），不是"切换"。

### 4.6.2 FR-9 预览处理器宿主落地口径（2026-11-09，P6-2）

**做了什么**：`PreviewKind.Shell` 这一路不再只有缩略图。系统里给该扩展名注册过
预览处理器的，拉起处理器并把它的窗口嵌进预览栏——PDF 能翻页、视频能播、Office 能看全篇。

**先摸清的事实**（`tools/preview-probe`，一次性探针，不进解决方案）：本机注册的处理器
**全是 32 位 in-proc DLL**（搜狗 PDF、金山看图、WPS 压缩包），而本程序是 x64。
理论上跨位宽 in-proc 加载不可能，但这三个 CLSID 的 `AppID` 都配了
`DllSurrogate = SysWOW64\prevhost.exe`，于是 COM 会把 32 位 DLL 加载进代理进程、
64 位客户端通过代理调用。探针实测：`IPreviewHandler` / `IInitializeWithFile` /
`IObjectWithSite` 全部 QI 成功，`IInitializeWithItem` 一律 `E_NOINTERFACE`。
**结论：不需要另起 32 位宿主进程**，直接用系统代理即可。

| 点 | 做法 | 理由 |
|---|---|---|
| 查注册表 | 64 位与 32 位视图都查，64 位优先 | 处理器注册在哪个视图取决于它的位宽，不是取决于我们的进程；只查一个视图会得到"没有处理器" |
| CLSID 校验 | 键存在但 `CLSID\{…}` 不存在 → 当没有处理器 | 卸载残留很常见（本机 `.docx` 就是这样）。不校验的话每次选中都白跑一次 `REGDB_E_CLASSNOTREG` |
| 初始化接口 | 只用 `IInitializeWithFile` | 三类处理器实测都支持它；`IInitializeWithItem` 要构造 `IShellItem`，`IInitializeWithStream` 要自己开流，收益不成比例 |
| 处理器线程 | 独立 STA，自建窗口、自跑消息循环 | 第三方 DLL 里 `DoPreview` 做什么我们说了不算。放 UI 线程上，一个卡住的处理器就是整个窗口假死 |
| 站点（`IObjectWithSite`） | 用托管 CCW 实现，`IObjectWithSite.SetSite` 走裸 vtable 调用 | 同一程序集里不能出现两个同 GUID 的接口（调用侧 `[ComImport]` + 实现侧托管接口会撞），所以调用侧按槽位取函数指针，实现侧才用带 GUID 的接口 |
| 加速键 | `GetWindowContext` 返回空加速键表，`TranslateAccelerator` 恒 `S_FALSE` | 处理器抢键会让主窗口的方向键、`Ctrl+C` 失灵。预览栏不参与键盘导航 |
| 子窗口尺寸 | 每次 `SetRect` 前把处理器窗口摆成容器客户区大小 | 漏这一句的表现是"什么都没画"——它确实画了，画在 1×1 里 |
| 重复打开 | 同一路径 + 同一 CLSID 且线程还活着 → 直接返回 | 重开要重新拉起 `prevhost.exe`、重新解析文件，用户看到预览区闪一下白 |
| "正在准备" | 写脚注，不写内容区 | 处理器窗口是 `HwndHost`，一出现就把内容区整块盖住（空域），写在里面等于看不见 |
| 失败处理 | 按**扩展名**记黑名单（会话内）+ 回落缩略图 + 脚注说明 | 按路径记会在翻文件夹时反复重试同一类；不说明的话用户会以为 PDF 只有一页 |
| 回调时序 | `HandlerReady` / `HandlerFailed` 先判 `_hasHandler` | 处理器可能在我们已经切走之后才回报，迟到的失败不能拿去标记另一个文件 |

**已知限制（明确留白）**：同进程内加载的 64 位处理器若在 `DoPreview` 里崩溃，会带走整个进程。
32 位处理器跑在 `prevhost.exe`，天然隔离。把 64 位那批也隔离需要独立宿主进程 +
跨进程窗口父化，属 P2。

**怎么验的**：`D:/ac05/handler_probe.py` 十三条断言，全部基于可观测事实——
视图模型状态（`handler` / 脚注是否清空）、窗口树（surface 是否存在、处理器有没有在
里面另开自己的窗口、尺寸对不对）、切换后 surface 是否消失。
**像素级确认在本机做不到**：桌面未激活，Qt 写的处理器不响应 `WM_PRINT`，
从窗口 DC 上 `BitBlt` 也只能拿到白色——这是环境限制，不是代码问题，
换到交互桌面应当人工看一眼。

### 4.6.3 FR-6.6 行内缩略图落地口径（2026-11-09，P6-2）

**做了什么**：列表里的图片与视频显示 24×24 的实际画面，其余类型仍是类型图标。

| 点 | 做法 | 理由 |
|---|---|---|
| 槽位大小 | 24，行高不动（32） | 把行高提到 36 会让"万项目录一秒扫完"变难；24 已经够认出"这是那张海报" |
| 哪些类型 | 只有位图与视频（`PreviewClassifier.SupportsThumbnail`） | PDF/Office 要拉起解析器、单页渲染，放在"每行一次"的场景里不值；那类由预览窗格负责，也正是 C14 的划分 |
| 触发时机 | 挂在行的 `Loaded`/`Unloaded` 上 | 虚拟化把行滚出视野就会触发 Unloaded，在途请求随之作废；滚回来重发（多半命中内存缓存）。比监听 `ItemContainerGenerator` 事件简单且不易漏 |
| 滚动闸门 | `ScrollChanged` → `Pause()`，停 160ms → `Resume()` | 滚起来时一个 Shell 调用都不发；闸门全局，两个窗格共用一个服务 |
| 大目录 | 条目数 >5000 一律只显示图标（T-03） | 由窗格按自己的条目集合计，不影响另一个窗格 |
| 网络路径 | 不出缩略图 | 1000 项共享目录 = 1000 次跨网往返；图标是本地生成的 |
| 缓存键 | 路径 + 大小 + 修改时间 + 目标像素 | 覆盖过的文件必须失效，否则显示的是已经不存在的画面 |
| 磁盘缓存 | `%LOCALAPPDATA%\Lingpane\cache\thumbs`，500MB，按写入时间淘汰到九成 | 用"最后访问时间"做 LRU 在 Windows 上不可靠（默认关闭更新），会得到一堆同样时间戳 |
| 写盘方式 | 先写 `.tmp` 再改名 | 进程在写一半时退出会留下损坏的半张图 |
| 内存层 | 512 张（约 18MB），LRU | 同一目录来回滚动是最高频动作，不该重复读盘 |

**设置界面**：§4.6.5 已补（FR-5.3.5），缓存引擎的占用显示、一键清除、上限调节三项齐了。

**怎么验的**：`D:/ac05/thumb_probe.py` —— 六张彩色渐变 PNG + 一张 1800×1200 大图 +
文本 + PDF，出图确认图片行是实际画面、文本与 PDF 仍是图标、列头与内容对齐；
缓存文件数首次 7、第二次仍是 7（第二次全部命中磁盘，没有重新问 Shell）。

### 4.6.4 FR-6.13 当前目录搜索落地口径（2026-11-09，P6-2）

**做了什么**：工具栏右侧一个常驻搜索框，按名称过滤**当前已加载的列表**；不递归、不读盘。

| 点 | 做法 | 理由 |
|---|---|---|
| 数据来源 | `_all`（本次枚举的原始结果） | 搜索不是第二次枚举。换目录才读盘，同一目录的 F5 与文件操作后的刷新都只重新过滤 |
| 匹配口径 | 子串、`OrdinalIgnoreCase`、空格分词后 **AND** | 与 `NaturalStringComparer`（列表名称排序）同一套大小写口径：排序认作相同的名字，搜索也得认得出来。文化敏感比较对子串匹配没有增益，却慢数倍 |
| 分词 | `string.Split(null)` 的空白重载 | 全角空格（U+3000）一并拆开——中文用户从文档里粘过来的关键词常带它，不拆就成了一个永远匹配不上的词 |
| 防抖 | 250ms，`Task.Delay` + CTS 取消 | 不用 `DispatcherTimer`，视图模型就能单独测；清空**不走防抖**，删掉最后一个字符要让完整列表立刻回来 |
| 线程 | 后台线程过滤，UI 线程只换 `Entries` | 需求写明。1 万项 `IndexOf` 约 2ms，10 万项就该到两位数了 |
| 快照 | `_all.ToArray()` 后再交给后台 | 遍历期间 UI 线程可能 `_all.Sort()`（原地排序）或整个换掉它，直接传会抛"集合被修改"，而那种异常出现在后台任务里只表现为一次静默的空白列表 |
| 结果上限 | 1000 条，命中总数照实统计 | 状态栏说"匹配 12000 项，仅显示前 1000 项"；超出的部分用户翻不到，但每条都要建行容器 |
| 与排序共存 | 过滤保持源顺序 | 排序在枚举阶段已完成，过滤只做取舍；重排会让"按大小排序后搜索"变成另一种顺序 |
| 与标签共存 | 条目对象复用，不重建 | 圆点跟着行走，不需要为搜索结果再查一次标签库 |
| 换目录 | 清空搜索 | 搜索范围是"这个目录里的这些条目"，换个目录还留着词只会得到莫名其妙的空列表 |
| 同目录刷新 | **保留**搜索 | 否则"删掉搜到的一项之后搜索框自己空了"，用户还得把词重打一遍。落地口径里点名的"过滤态下文件操作仍可用"就是靠这一条 |
| 宽度 | 三档 150 / 120 / 72，按窗格实际宽度切 | 分屏后每格只剩约 420px，工具栏还挤着四个导航按钮、地址栏与三个视图按钮；固定 150 会把地址栏压到 0（实测一条面包屑都看不到）。连续缩放会让输入框跟着拖拽一直抖，三档"切分屏时变一次"是看得懂的 |
| 窄窗格装饰 | <520px 时收起放大镜、清除按钮与左右留白 | 72px 里再放两个图标就只剩十几个像素显示文字。功能不损失：Esc 仍能清空、Ctrl+F 仍能聚焦 |
| 键位 | `Ctrl+F` 聚焦并全选；`Esc` 清空（空时回列表）；`Enter`/`↓` 跳到结果第一项 | 与资源管理器一致 |

**没做的**：通配符与"内容搜索"。需求只写"按名称过滤"，加通配符要额外的语法说明与转义规则，
而 `*` 在文件名里本来就是合法字符；全盘/递归搜索在 §七 黑名单里。

**怎么验的**：`tools/offscreen` 新增 `--path / --search / --then-search / --then-refresh /
--then-path / --then-escape / --split`，全部读值不靠看图：

| 场景 | 观察点 |
|---|---|
| 100 项目录搜 `file_1` | 命中 12 项，状态栏"匹配 12 项，共 100 项" |
| 10000 项目录搜 `0` | `visible=1000`，状态栏"匹配 10000 项，仅显示前 1000 项" |
| 搜不存在的词 | 列表空态显示"没有匹配的项"，状态栏"匹配 0 项" |
| 清空（`--then-search ""`） | 回到 100 项，状态栏"100 项 · 枚举 3 ms" |
| 同目录刷新 | 搜索词保留，命中数不变 |
| 换目录 | 搜索词清空，列表换成新目录 |
| Esc | 同上（直接调 `OnSearchKeyDown`，离屏桌面发不了真按键） |
| 分屏 50/50 | 搜索框收到 72px、装饰收起，左窗格地址栏仍显示盘符、右窗格显示到第二段 |

### 4.6.5 FR-5.3.5 缩略图缓存设置落地口径（2026-11-09，P6 收尾）

**做了什么**：设置页隐私分节里新增「缩略图缓存」一段——占用行、上限下拉框、清除按钮。
引擎（`ThumbnailCache.Measure/Clear/Trim`）在 FR-6.6 就已就位，这一批只补界面与接线。

| 点 | 做法 | 理由 |
|---|---|---|
| 占用统计时机 | 首帧后异步跑（`Loaded` 里 `Task.Run(Measure)`） | 缓存目录上万个小文件，即便元数据已在系统缓存里也是几十到几百毫秒；放 UI 线程上就是"打开设置页卡一下" |
| 上限取值 | 五档 128/256/500/1024/2048，默认 500 | 与 `ThumbnailCache.DefaultCapBytes` 是同一个数。改动前设置默认写 512、引擎默认 500，两处对不上 |
| 非标准值 | 打开设置页时吸附到最近一档并落盘 | 旧版本留下的 512 不在档位里。不吸附的话下拉框显示 1024、占用行写上限 512 MB、实际按 512 淘汰——三个数字各说一套 |
| 调低上限 | 立刻 `Trim(cap)` 再 `Measure`，不等"攒满 200 次写入" | 2048 改成 128 之后磁盘上仍占 2GB、要等下一次自动淘汰才动，用户会当成设置没生效 |
| 上限注入 | `App` 启动读到设置后写一次 `ThumbnailCache.CapBytes` | 缓存是"到处都在写"的静态设施（缩略图服务、预览、列表滚动），为这一个数字沿调用链加参数得不偿失 |
| 清除前确认 | 确认框写明"将删除 N"与"文件本身不受影响" | 只说"已清除"，用户无法判断这条命令到底做没做；而在文件管理器里"清除缓存"听起来像会动文件 |
| 清除失败 | 清完再量一次，剩下的说"有 N 未能删除（可能正被占用）" | `Clear` 吞掉所有 IO 异常（缓存清不掉不该影响可见功能），成没成只能靠再量一次判断 |
| 状态行 | 无内容时折叠（`Text` 为空的触发器） | 这一行夹在两个分组之间，空着就是一段来源不明的空白，看起来像漏了控件。用触发器而不是在七个赋值点各置一次 `Visibility` |
| 淘汰策略 | 抽成纯函数 `PlanTrim`，`Trim` 调它 | 原来"淘汰到九成"只能在磁盘上造 500MB 才验得了；上限变成用户可调之后，边界会被人一个个试过去，得有断言兜着 |

**没做的**：上限的自定义输入（只给五档）。需求写的是"上限设置"，五档覆盖 128MB–2GB 够用；
自由输入还要处理"填了 0 / 填了 100000"，收益不如直接给档位。

**怎么验的**：
- 10 条单测（`ThumbnailCacheTests`）：空列表、未超上限、**刚好等于上限**、超上限删到九成、
  最旧优先、同时间戳按输入顺序、单文件超上限、`capBytes=0` 取生效值、`CapBytes` 拒非正数、
  默认值与设置默认一致。
- 走查 `--settings --scroll-to ThumbCacheText`：中/英 × 深/浅四张截图，占用行、下拉框、提示、
  按钮排布正常，无裁切与重叠。
- **真实淘汰**：往缓存目录塞 30 个 5MB 假文件（稀疏文件，mtime 设成 2020）把占用顶到 151MB，
  再用 `--cache-limit 128` 在下拉框里真的选一档 → 占用 151MB→115.2MB、文件 52→45、
  状态行"上限已改为 128 MB，当前占用 115.2 MB"；22 张真实缩略图（mtime 最新）一张未动。
  随后删掉假文件、上限改回 500，缓存恢复 22 个 / 168.8 KB。
- 设置文件复核：`settings.json` 里的 `cacheLimitMb` 从旧值 512 被吸附为 500。

**实现口径（走查后的最终形态）**

| 点 | 做法 | 理由 |
|---|---|---|
| 主页的表示 | `TabHostViewModel.HomeMarker = "lingpane:home"` 哨兵写进 `session.tabs` | 空串在会话里表示"这一项无效"，混用会让主页被当坏数据丢掉 |
| 主页切换 | 不调 `PreparePendingPath`；`PaneViewModel.DetachToHome()` 丢路径但**保留历史栈** | 否则 `HasPendingContent` 被置真，会拿空路径去读盘；历史栈要留给 Alt+← |
| 已知文件夹 | 七个 FOLDERID 走 `SHGetKnownFolderPath`，结果整份缓存进 `general.knownFolderPaths` | `Environment.SpecialFolder` 没有 Downloads，且用户重定向/OneDrive 接管后给的是旧路径 |
| 缓存校验 | 命中（路径仍存在）就不碰 shell32；首帧之后 `ApplicationIdle` 后台校验，变化才刷 UI + 落盘 | 不占首帧 |
| 容量 | `DriveInfo` 在线程池 + `Task.WhenAny(probe, Task.Delay(2s))` | 断线的映射盘会让 `DriveInfo` 卡几十秒 |
| 失效检测 | 异步（沿用 FR-7.7 的口径） | UNC 不可达要等几秒，同步做会卡住主页首帧 |
| 视图模型 | 窗口级单例，所有主页标签共用一份；`HomeView` 同样一份实例 | 最近访问与收藏本来就是全局数据 |

**踩到的坑（写下来避免复现）**

- `ProgressBar.Value` 默认是 **TwoWay** 绑定，绑到只读属性 `UsedRatio` 会抛 `XamlParseException`。
  必须显式写 `Mode=OneWay`。更麻烦的是它的表现形式：异常在布局过程中抛出，WPF 的整个 measure/arrange
  被打断，于是"点卡片后主区域一片空白"——看起来像布局 bug，实际是模板绑定错误。
- `TabStrip` 的图标不能写成元素上的 `Text="{Binding IconGlyph}"`：本地值优先级高于触发器，
  会把图钉的高亮触发器压掉。要放进 `<Setter>`。

1. **"显示系统文件"是独立的一位，不是隐藏文件的子集。** 需求 FR-5.2.4 把它们列成三项，
   落地时确认必须分开：`pagefile.sys` 与"以点开头的配置目录"是两种意图，
   共用一个开关必然有一边不合意。带 H+S 的条目（`desktop.ini`）要两个开关都开才出现，
   判据写成"逐位否掉"而不是"任一位允许就显示"。
2. **单击打开的悬停延迟用附加属性门控，不改 `IsMouseOver`。** 后者是只读的，
   改不了。`RowHover.IsHovered` 由 `PaneView` 按设置置位（双击模式 0ms、单击模式 600ms），
   而行样式要求 `IsMouseOver && IsHovered` **同时**成立才画高亮——
   这一条顺带解决了虚拟化容器复用导致的"假高亮残留"。
3. **"确认"拆成删除与批量两项，覆盖那一项暂不落地。** 需求 FR-5.2.8 写了三项，
   但当前复制/移动遇到同名一律自动改名（`FileOperations.UniqueName`），
   没有覆盖路径可供确认。挂一个不生效的开关比不做更糟，等覆盖式粘贴进来再补。
4. **启动恢复做成两个下拉联动，而不是三选一。** 工作区是"多个里挑一个"，
   与"不恢复/恢复会话"不是同一维度的枚举：硬塞进一个下拉会让"选了工作区"变成第 3 项，
   而第 4 个工作区就没有位置了。两处互斥由界面当场同步 + `Normalize()` 兜底。
5. **强调色只覆盖应用资源顶层的四个画刷。** 不去改主题字典（那份是共享的，
   切一次主题就被换掉），也不碰 `Color.Accent.*`（主题字典内部的 `StaticResource`，
   改了传不到已冻结的画刷上）。派生色不落盘，`ThemeService.Apply` 末尾重算一次浅底。
6. **"恢复默认"只重置偏好，不动用户数据。** 收藏、历史、标签、工作区是用户攒下来的东西，
   用"恢复默认"删掉它们不可接受。另外 `History` 与 `Bookmarks` 两段不换对象——
   `VisitHistory` / `BookmarkStore` 持有它们的引用，换对象会让它们继续读写旧实例。
7. **清理失效标记的破坏面写在确认框里。** 判据是"用记录里的路径重新 Identify，结果与记录一致"
   （只判存在不够：同卷移动后原地被新文件占用，路径还在但已经是另一个文件）。
   离线磁盘上的标记同样会被清掉，这一点必须事先讲明。

### 4.10 FR-10.7 可访问性（1 天）

- 先做 §3.6 的焦点可视化，否则后面全是空谈。
- 主要控件补 `AutomationProperties.Name`（列表、导航栏、标签栏、地址栏、状态栏）。
- `Tab` 顺序手工走一遍：地址栏 → 列表 → 导航栏 → 标签栏，`Tab` 不陷入死循环（列表内的 `Tab` 让给窗格切换）。
- 屏幕阅读器只要求"能读出主要控件"，不做完整 UIA 实现。

**落地口径（2026-11-09）**

1. **标签栏原先根本进不去。** `TabItems` 是个 `ItemsControl`，`Control` 默认 `Focusable=True`，
   于是它抢到一个停靠点，但没有任何按键处理——Tab 走到这里就再也出不去。
   改成容器不可聚焦、每个标签可聚焦：Enter/Space 切换、左右键在标签间移动，
   Tab 走完所有标签后自然离开。关闭按钮退出 Tab 序列（12 个标签会有 12 颗关闭按钮）。
2. **列表必须整块一个停靠点。** 默认每个 `ListBoxItem` 都是停靠点，万项目录里
   Tab 要按一万下才出得去。现在列表整块只停一次，项间移动交给方向键。
   同一条也适用于导航栏。
3. **标签项的焦点环要自己画。** `FocusVisualStyle` 是 `Control` 的属性，标签是 `Border`，
   用不了；在模板里画一条内描边并绑 `IsKeyboardFocused`，鼠标点不亮、键盘走到才亮。
4. **Tab 顺序保留实测顺序，不按计划里的写法硬改。** 实测是
   标签栏 → 导航 → 工具栏/地址 → 列头 → 列表 → 预览。计划里那句"地址栏 → 列表 → 导航栏 → 标签栏"
   要跨可视树分支重排：WPF 的 Tab 排序按可视树分层，跨分支改序得动整棵树；
   而且把内容区提到 chrome 之前本身就违反视觉顺序，WCAG 2.4.3 要的是"与视觉顺序一致"。
   实测顺序就是从左到右、从上到下，照着保留，并在 `docs/shortcuts.md` 里写明。
5. **焦点框的像素确认做不了，与本机预览处理器那一条同类。** WPF 只在真按过键之后才画
   焦点视觉（`KeyboardNavigation.ShowKeyboardCues` 是 internal，程序化置不上），
   离屏进程里截图永远是"没有焦点框"。走查能给的是结构化证据：18 个停靠点里
   17 个挂着自定义焦点样式（第 18 个是标签 Border，自绘内描边），
   加上"没有任何模板再写 `FocusVisualStyle={x:Null}`"。像素级确认留给有交互桌面的机器。
