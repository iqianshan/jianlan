# ADR-0007：覆盖图标只做快捷方式，且走已经在跑的图标解析通道

- 状态：已接受
- 日期：2026-11-05
- 相关：FR-6.5、ADR-0006（目录图标）、`Shell/ShellIconProvider.cs`、`Services/FolderIcons.cs`

## 背景

FR-6.5 要求"覆盖图标（快捷方式箭头、共享标记）"。实现前要先确认两件事：
**Shell 的覆盖层能不能省掉磁盘查询**，以及**哪些覆盖类型是可靠的**。

## 实测（2026-11-05，本机 Windows 11）

### 1. `SHGFI_LINKOVERLAY` 在"按扩展名"模式下不可用

按类型查询（`SHGFI_USEFILEATTRIBUTES`）时追加 `SHGFI_LINKOVERLAY`：

| 类型 | 不带覆盖 | 带覆盖 | 图标是否变化 |
|---|---|---|---|
| `.lnk` | 序号 0 | 序号 0 | 无 |
| `.url` | 序号 50 | 序号 50 | 无 |
| `.txt` | 序号 51 | 序号 51 | 无 |
| `.exe` | 序号 2 | 序号 2 | **位图变了**（多了箭头） |

结论：
- `.lnk` / `.url` 的**类型图标本身已经带箭头**（对照位图确认：空白页+箭头、地球+箭头），
  再加 `LINKOVERLAY` 是重复劳动；
- 该标志在 `.exe` 上确实生效，但对普通程序加箭头是**错误语义**——只有快捷方式才该带箭头；
- 因此"按扩展名 + 覆盖标志"这条路走不通，它既不能给快捷方式加分，还会给别的类型加错。

### 2. 按真实路径解析 `.lnk` 才能拿到目标图标

`SHParseDisplayName` + `SHGetFileInfo(SHGFI_PIDL)`：

| 文件 | 图标序号 | 位图 |
|---|---|---|
| `Google Chrome.lnk` | 50 | Chrome 彩色圆环 + 左下箭头 |
| `Obsidian.lnk` | 51 | 紫色宝石 + 箭头 |
| `TRAE Work CN.lnk` | 52 | 程序图标 + 箭头 |

Shell 在解析链接时已经把目标图标与箭头一起合成好了，**不需要自己叠图**。

## 结论

### 1. 只对 `.lnk` / `.url` 按真实路径解析，其余扩展名保持按类型

按类型只能画出"通用快捷方式"，所有快捷方式长得一样——这一眼就能看出与资源管理器不一致。
按真实路径能把目标程序图标取回来，代价是一次磁盘查询。

### 2. 复用 ADR-0006 的后台通道，不新增机制

`FolderIcons.Resolve` 原本只处理目录，现在同一个循环里兼顾快捷方式，因此自动继承三条限制：

1. 只处理本地盘路径（UNC 一律跳过）；
2. 每次导航最多 240 项（目录与快捷方式共享配额）；
3. 与"按类型解析出的序号"相同则丢弃——解析不出目标图标（链接损坏、目标无权访问）
   时序号会回落到类型图标，此时不写回界面。

时序上仍在 `DispatcherPriority.ApplicationIdle` 之后、后台线程执行，首帧路径不新增 IO。

### 3. 共享标记、云同步状态、杀软状态一律不做

| 覆盖类型 | 做不做 | 理由 |
|---|---|---|
| 快捷方式箭头 | ✅ | 按类型可推断，且能缓存；解析一次得到"目标图标+箭头" |
| 共享标记 | ❌ | 与具体文件的共享状态绑定，必须按文件查 |
| 云同步状态（OneDrive 等） | ❌ | 需 `SHGFI_OVERLAYINDEX` + 实时状态，每项一次查询 |
| 杀软 / 版本控制 | ❌ | 由第三方扩展提供，内容与开销都不可控 |

后三类在万项目录下等于"每个可见项一次磁盘查询"，直接违反 NF-01 与 R-08（滚动流畅）。
需求里的"共享标记"据此标注为不做，理由记录在 §8.3 黑名单。

## 已知代价

1. 目录里 `.lnk` 超过 240 个时，靠后的仍是通用快捷方式图标；
2. 每次刷新/导航都会重新解析一遍（未做跨导航缓存，避免为几万个链接常驻字符串）；
3. 解析结果按图标序号去重，同一目标的多个快捷方式共用一张位图（这是收益，不是代价）。

## 实测

- 桌面 10 个快捷方式：改造前全部显示同一个"空白页+箭头"，改造后各自显示目标程序图标 + 箭头，
  与资源管理器逐项一致 ✅
- 首帧与启动耗时：与改动前二进制交替测量无差异（解析在空闲期，见 `docs/performance-gate.md` §11）
