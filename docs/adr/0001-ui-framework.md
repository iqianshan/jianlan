# ADR-0001：UI 框架选用 WPF

- 状态：**已接受**（2026-11-03）
- 影响：全部 UI 层，不可局部替换

## 背景

项目核心目标是"启动快、稳定"。原定冷启动指标 P50 ≤ 400 ms。候选 UI 框架：

| 方案 | 启动 | Shell 互操作 | 深色/高对比度 | 生态资料 |
|---|---|---|---|---|
| WPF | ? | 最厚 | 原生 | 极大 |
| WinUI 3 | 800 ms+ | 一般 | 原生 | 中 |
| WinForms | ? | 厚 | **需全自绘** | 大但偏老 |
| Tauri / Electron | 400 ms+ | 几乎为零 | 容易 | 中 |

## 决策依据（实测，非估算）

Release + ReadyToRun，AMD Ryzen 7 PRO 5850U / Windows 11，同机对照，各 3–5 次：

| 方案 | 进程启动 → 窗口可交互 |
|---|---|
| WinForms 最小空窗口 | **214–330 ms** |
| WPF 最小空窗口（默认） | 1030–1120 ms |
| WPF 最小空窗口（禁 IME） | **541–665 ms** |
| WPF `HwndSource` 直建（绕过 `Application`/`Window`） | 978–1051 ms |
| Lingpane M0（禁 IME） | 574–649 ms |

关键发现：

1. **1.1 秒是 WPF 框架基线**，与业务代码无关——最小空窗口就是这个数。
2. 单项最大成本是**中文输入法上下文创建**，约 500 ms，同时占用约 43 MB 工作集。
   启动期关闭 IME 可回到 600 ms。
3. 绕过 `Application` / `Window` 类没有收益：慢的是首次渲染管线初始化，不是窗口类本身。
4. 业务代码自身增量约 0–60 ms（资源字典 100–150 ms 是唯一可压缩项）。

## 决定

**继续使用 WPF。** 但明确接受以下代价与对应措施：

| 代价 | 措施 |
|---|---|
| 启动基线比 WinForms 高约 350 ms | 冷启动指标由 400 ms 调整为 **P50 ≤ 700 ms** |
| 中文 IME 初始化占 500 ms | 启动期 `InputMethod.SetIsInputMethodEnabled(window, false)`，首次文本输入场景再启用 |
| 仍高于 Everything（<150 ms） | 不与之竞争；定位是 Explorer 的日常替代，不是索引工具 |

## 备选方案与不选的理由

**WinForms**：启动最快（214–330 ms），图标与右键菜单同样成熟。否决原因是需求明确要求深色 +
高对比度三主题，WinForms 下几乎全部控件需自绘，工作量与出错面远大于省下的 350 ms。

**WinUI 3**：基线 800 ms 以上（MUX 初始化 + WinRT 激活），必然超标。

**Tauri**：Shell 互操作需自行写 unsafe 绑定，COM 释放与句柄泄漏的 bug 表现为"用几小时后变卡"，
与稳定性目标直接冲突。

## 后果

- 冷启动指标改为 P50 ≤ 700 ms / P95 ≤ 900 ms，写入门禁
- 若后续发现启动不达标，**优先查 IME 与资源字典**，不要怀疑业务代码
- 若将来 WinForms 重新进入讨论，前提是"放弃深色模式"或"接受自绘全部控件"

## 复查条件

出现以下任一情况时重新评估：

1. 除 IME 外，实测启动仍高于 900 ms
2. .NET 后续版本改进 WPF 首帧开销（届时复测 §决策依据 表格）
3. 需求去掉深色模式要求
