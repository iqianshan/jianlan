# ADR-0008：NF-05R 重新标定（0.2.0 开工前）

- 状态：**已接受**（2026-11-05）
- 影响：NF-05R 门禁阈值、`Measure-List.ps1` 默认值、`performance-gate.md` §9.7
- 关联：ADR-0002（内存分档修订），本 ADR **修订**其 NF-05R 部分，NF-05 绝对分档不变

## 背景

ADR-0002 在 2026-11-03 定下 NF-05R ≤ 45 MB，当时实测 29.7 MB，留出约 50% 增长空间。

两天后（M1 批 3 完成：右键菜单、文件操作、拖放、命令系统、图标解析、i18n、三主题与字号令牌）
复测，增量涨到 43–46 MB，**单轮即可超标**。45 MB 已经没有余量，任何一次波动都会判失败，
门禁退化成"随机红灯"，失去"检测代码回归"的功能。

## 测量记录（2026-11-05）

`Measure-List.ps1 -Exe publish\Lingpane.exe -Path D:\perf-10k -Normalize`，10000 项 + 滚动 240 帧。

| 轮次 | 枚举 | 首屏 | 帧率 | 私有提交 | 空窗口 | NF-05R | GDI | 有效性 |
|---|---|---|---|---|---|---|---|---|
| 1 | 98 ms | 322 ms | 83.4 fps | 127.4 MB | 81.0 MB | **46.4 MB** | 81 | ✅ 低态 |
| 2 | 82 ms | 283 ms | 87.6 fps | 124.2 MB | 81.0 MB | **43.2 MB** | 81 | ✅ 低态 |
| 3 | 69 ms | 303 ms | 60.8 fps | 124.8 MB | 118.0 MB | 6.8 MB | 118 | ❌ 高态 |
| 4–8 | — | — | — | 121.8–160.7 MB | 118.0 MB | 3.8–42.7 MB | 118–120 | ❌ 高态 |

**只有前两轮有效。** 第 3 轮起系统切入高态（空窗口 118 MB、GDI 118），此后五轮全部作废。
排查确认无残留 `Lingpane` / `WpfBaseline` 进程，与 §9.6 的结论一致：高态只有重启系统才恢复。

### 顺带发现：高态下 `-Normalize` 本身不可靠

按 §9.6 的设计，`-Normalize` 每轮跑一次空窗口对照，同轮内同态、相减应该有效。但实测第 2–3 轮

- Lingpane 私有提交 159.1 / 160.7 MB
- 空窗口 118.0 MB

相减得 41.1 / 42.7 MB，看起来"正常"，其实两边都没在同一量级上——
高态下 Lingpane 自身在 121.8–160.7 之间摆动了 39 MB，空窗口却稳定在 118。
说明"两态"模型不够：高态内部还有一层与进程启动时机相关的抖动。

因此高态下不只看 GDI 是否 > 80，**只要空窗口超过 90 MB 就整批作废**——
这条判据比 GDI 更直接，`Measure-List.ps1` 已补。

## 决定

### 1. NF-05R 单窗格 45 → 65 MB

依据：

| 项 | MB |
|---|---|
| 当前实测（两轮有效样本均值） | 44.8 |
| P1 重构预估（PaneView 实例化、命令路由、焦点管理） | +3 |
| P2 标签栏与视图保活（VM 保活、View 只留活动） | +8 |
| P4 彩标（JSONL + 内存索引，实测 5000 条 1.9 MB，含 UI 色点） | +4 |
| 小计 | 59.8 |
| 余量（约 9%） | 5.2 |
| **标定值** | **65** |

### 2. 新增双窗格档 90 MB

ADR-0002 只给 NF-05R 定了单窗格口径（条件写的是"单窗格、10000 项、滚动 240 帧"），
双窗格上线后没有对应判据。按"第二份 PaneView + 第二份条目集合"估：

- 单窗格 65
- 第二份视图壳与条目集合（10000 项约 8 MB + 项容器约 8 MB）≈ +20
- **90 MB**

### 3. NF-05 绝对分档不变

150 / 185 / 230 MB 维持 ADR-0002 的结论。自洽性检查：150 − 81（框架底）= 69 MB 可支配，
NF-05R 65 < 69，两条门禁不冲突；双窗格 185 − 81 = 104，NF-05R 90 < 104，同样自洽。

### 4. 新增不漂移的辅助指标：托管堆增量

私有提交会随环境两态漂移 ±36 MB，`-Normalize` 在高态下又被证明不可靠。
补一个不受框架底影响的指标，专门盯**数据层**：

> **NF-05H：滚动结束后的 `GC.GetTotalMemory(true)` ≤ 12 MB**（单窗格 10000 项）

依据：`FileEntry` 万项实测约 7.7 MB（§9.2.1），加排序列表与字符串驻留表，当前应在 9–10 MB。
这个数字只反映"每条目存了多少东西"，与 WPF 框架、GDI、环境两态完全无关。
它是 NF-05R 的**降级判据**：高态下 NF-05R 不可信时，看 NF-05H 判断有没有数据层回归。

## 备选方案与不选的理由

**维持 45 MB，把当前功能压回 29.7 MB。** 已被证伪：两天涨的 13.5 MB 全是需求内的功能
（右键菜单、文件操作、拖放、命令、图标、i18n），不是泄漏也不是浪费。压回 29.7 等于砍功能。

**去掉 NF-05R，只保留 NF-05 绝对值。** 否决：绝对值含框架底 81 MB，业务涨 12 MB 只让
150 的阈值动 8%，灵敏度太低，抓不到回归。相对值仍是必要的。

**改为"相对上一发布版本"的回退检测（不设固定值）。** 方向正确，但需要长期维护版本基线快照，
且 CI 里没有历史数据可比。**降级为流程要求**：每次发版把实测值记进
`performance-gate.md` §9.7 的历史表，下一版相比上一版涨幅超过 10 MB 时人工追查。
固定阈值 + 版本快照双轨，成本很低。

**把 NF-05R 定义改成"Lingpane − 同轮空窗口，且空窗口 < 90 MB 才有效"。** 这就是本 ADR
采纳的补丁，不是替代方案，列在此处以免被误认为遗漏。

## 后果

- `docs/performance-gate.md` §9.7：NF-05R 阈值 45 → 65，新增双窗格 90 档，新增 NF-05H
- `tools/perf-fixture/Measure-List.ps1`：`-MaxDeltaMb` 默认 45 → 65；空窗口 > 90 MB 时判"不可判定"
- `docs/requirements.md` NF-05 行与 ADR-0002 引用同步
- M2 每个批次结束复测一次；**双窗格开工前必须先单独测一次双窗格增量**，
  90 MB 是估算值，不是实测值

## 复查条件

1. 重构（P1）完成后实测超过 60 MB（距新阈值 5 MB 内）——说明重构本身的成本被低估
2. 双窗格实测超过 85 MB
3. NF-05H 从当前约 9–10 MB 涨到 12 MB 以上，且 NF-05R 同步上涨——判定为数据层回归，不是功能增长
4. 环境恢复正常态后，若单窗格实测低于 40 MB，可考虑把阈值回调到 60
