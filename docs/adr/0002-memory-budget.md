# ADR-0002：NF-05 内存分档修订

- 状态：**已接受**（2026-11-03）
- 影响：NF-05 门禁、M1 功能预算、性能文档 §9
- 关联：ADR-0001（UI 框架选用 WPF）

## 背景

原 NF-05 分档为：单窗格 ≤ 120 MB、双窗格 ≤ 150 MB、预览窗格 ≤ 190 MB。
这组数字定于 M0 规划阶段，当时按"基础占用约 70 MB + 每万项若干"估算，没有实测支撑。

M0.5 实测后出现两个事实：

1. **框架底是 81.0 MB。** 用纯 WPF 空窗口对照程序（`tools/env-check/WpfBaseline`，
   不含任何业务代码）测得私有提交 81.0 MB。空目录 93.0 MB 里，本项目自己的
   代码、资源字典、窗口结构合计只有 **12.0 MB**。
2. **120 MB 只剩 9.3 MB 余量。** 10000 项目录滚动后为 110.7 MB（已优化过，见
   performance-gate §9.2.1），距 120 MB 仅 9.3 MB。

也就是说：**81 MB 框架成本吃掉了 120 MB 预算的 68%，只给业务功能留下 39 MB。**
这不是代码写坏了，而是阈值与所选框架不匹配。M1 要增加标签栏、地址栏、右键菜单、
命令系统与设置持久化，按现有余量必然突破，突破后无法判断是功能超支还是代码退化。

## 决策依据（实测，非估算）

AMD Ryzen 7 PRO 5850U / Windows 11 / .NET 9 Release + R2R，私有提交口径，正常测量态（GDI < 80）：

| 测量对象 | 私有提交 | 说明 |
|---|---|---|
| 纯 WPF 空窗口 | **81.0 MB** | 框架固定成本，任何 WPF 应用都要先付 |
| Lingpane 空目录 | 93.0 MB | +12.0 MB 为自制部分 |
| Lingpane 10000 项（只加载） | 102.6 MB | 数据层 +9.6 MB |
| Lingpane 10000 项（滚动 240 帧） | 110.7 MB | 项容器 + 约 8 MB |
| Windows Explorer（同机同刻） | 336.4 MB | 外部参照，见下方说明 |

关于 Explorer 参照的限定：该进程同时承载桌面、任务栏与外壳服务，
不等于"单个文件窗口"的成本，**只作数量级参照，不作为阈值依据**。
它能说明的只有一件事：150 MB 量级仍显著低于系统自带资源管理器。

## 决定

### 1. 绝对值分档上调

| 场景 | 原阈值 | **新阈值** | 当前实测 | 余量 |
|---|---|---|---|---|
| 单窗格 + 10000 项 + 滚动 | 120 MB | **150 MB** | 110.7 MB | 39.3 MB |
| 双窗格，各 10000 项 | 150 MB | **185 MB** | 预估约 130 MB | 约 55 MB |
| 开启预览窗格 | 190 MB | **230 MB** | 预估约 160 MB | 约 70 MB |

上调幅度 25% / 23% / 21%，把"框架底 81 MB"从被压缩的预算里释放出来：
新分档下可支配额度为 150 − 81 = **69 MB**，当前业务实际占用 29.7 MB，占 43%，
给 M1 留出约一倍的增量空间，而不至于宽到失去约束意义。

### 2. 新增相对增量门禁 NF-05R

绝对值会随框架底与测量环境漂移（见 performance-gate §9.6，同一 exe 存在相差 36 MB 的两态），
因此同时引入一个**不随环境漂移**的相对判据：

> **NF-05R：Lingpane 私有提交 − 纯 WPF 空窗口私有提交 ≤ 45 MB**
> （条件：单窗格、10000 项、滚动 240 帧）

当前实测 29.7 MB。45 MB 相当于留出 15.3 MB（约 50%）增长空间。

两条门禁的分工必须写进文档，否则会被混用：

| 门禁 | 回答的问题 | 超标时的含义 |
|---|---|---|
| NF-05（绝对） | 用户会不会觉得这软件吃内存 | 功能预算超支，需要砍功能或优化 |
| NF-05R（相对） | 这次代码改动有没有引入退化 | 代码问题，查数据层与视图层 |

**判定顺序：先看 NF-05R，再看 NF-05。** 相对值超标一律当代码回归处理，
绝对值超标才进入功能预算讨论。

### 3. 配套设计约束（不写下来，150 MB 撑不住）

上调阈值不等于可以随意占内存。三条约约束必须实现：

1. **非活动标签页不保留条目集合。** 只保留路径与滚动位置，切回时重新枚举
   （实测万项枚举 66 ms，用户无感）。若每个标签页各留 10000 项，
   10 个标签页就是 10 × 7.7 MB ≈ 77 MB，任何阈值都拦不住。
2. **右键菜单按需创建，关闭后释放。** 常驻内存成本计 0，打开瞬间峰值另计。
3. **预览窗格的解码必须设 `DecodePixelWidth`，且超预算时自动关闭预览**
   （原 R-05 规则不变，仅随分档同步上限）。

## 备选方案与不选的理由

**维持 120 MB，继续压缩占用。** 已被证伪：可支配部分总共 12 MB + 数据层增量，
优化 `FileEntry` 后万项目录只省下 8.1 MB（118.8 → 110.7），余量从 5.4 涨到 9.3。
继续压缩的下一刀只能砍功能（图标、缩略图、多标签），与需求冲突。
**天花板已经摸到，不是没优化，是没得优化。**

**改用 WinForms 以获得更低的框架底。** 否决理由同 ADR-0001：
深色 + 高对比度三主题在 WinForms 下需自绘全部控件，工作量与出错面远大于省下的内存。

**去掉绝对阈值，只保留相对增量。** 否决：绝对阈值是用户视角的承诺，
去掉后会出现"没人和用户解释为什么占了 400 MB"的情况。两者并存成本很低。

**按条目数线性给预算（如 10000 项给 130 MB、100000 项给 300 MB）。**
否决：条目数超过可视范围后，虚拟化使成本与总数弱相关（100 项 99.9 MB → 10000 项 102.6 MB），
线性预算会奖励"多塞条目"，与虚拟化的设计意图相反。

## 后果

- NF-05 三条分档上调为 150 / 185 / 230 MB，NF-05R 增加 45 MB 上限，写入门禁
- `requirements.md` NF-05 行与总预算核对段落、`performance-gate.md` §9 判定表同步更新
- M1 每个批次结束复测一次 NF-05R；相对增量连续两个批次逼近 40 MB 时，
  在开工第三批前先处理，不要等到 45 MB 才动作
- 若 M1 实测单窗格超过 140 MB（距阈值 10 MB 内），触发本 ADR 复查，
  不再重复"先上调阈值再看"的路径

## 复查条件

出现以下任一情况时重新评估：

1. M1 实测单窗格超过 140 MB，或双窗格超过 175 MB
2. 实现多标签后，10 个标签页同时打开的内存超过单标签的 1.5 倍
   （说明"非活动标签不保留条目"的约束没有真正生效）
3. 加入缩略图或预览后，NF-05R 相对增量超过 45 MB
4. 更换 UI 框架或 .NET 大版本升级，导致 81 MB 框架底发生明显变化
