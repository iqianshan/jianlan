# ADR-0004：不引入依赖注入容器

- 状态：**已接受**（2026-11-03）
- 影响：所有对象的构造方式、测试替身注入方式

## 背景

.NET 项目常默认引入 `Microsoft.Extensions.DependencyInjection`，用容器统一管理服务生命周期。
本项目的首要目标是**启动快**，任何启动期执行的代码都要先回答"能不能挪到 `Loaded` 之后"，
容器初始化恰好属于"启动期一次性成本"。

## 决定

**不使用 DI 容器。** 依赖通过构造函数直接传入，无参场景直接 `new`。
当前对象图：

| 对象 | 依赖 | 构造位置 |
|---|---|---|
| `MainViewModel` | 无 | `MainWindow` 字段初始化 |
| `ShellIconProvider` | 无（静态缓存） | 使用处 |
| `IconKeyToImageConverter` | 无 | 静态只读单例 |
| `FontScaleService` | 无 | 使用处 |

## 依据

1. **对象图深度为 1。** 全部服务都没有依赖，也没有生命周期需求（无 scoped/transient 之分）。
   容器能提供的价值（自动装配、生命周期管理、拦截）在这里一个都用不上。
2. **容器初始化是启动期净成本。** 构建 `ServiceProvider` 需要反射扫描与委托编译，
   量级在 20–30 ms 且完全落在启动路径上。用 20–30 ms 换取"少写几个 `new`"不划算。
3. **启动路径要能被逐行读懂。** `App` → `MainWindow` → `MainViewModel` 三跳就能看完，
   排查启动变慢时不需要理解容器解析链。这与 §11 的"环境变慢与代码回归区分"直接相关：
   启动路径越短，越容易判断是环境还是代码。
4. **测试不需要容器。** `Lingpane.Core` 无 UI 依赖，测试直接 `new` 被测对象；
   `Lingpane.App` 的视图层不做单元测试，用 `--perf-probe` 做端到端测量。

## 备选方案与不选的理由

**`Microsoft.Extensions.DependencyInjection`。** 增加约 20–30 ms 启动成本与一个 NuGet 依赖，
换来的能力当前全部用不上。

**手写轻量容器（静态 ServiceLocator）。** 比直接 `new` 更难追踪：依赖变成隐式的，
读代码时看不出谁依赖谁，排查启动问题时反而更慢。

**社区容器（Autofac / DryIoc，可预编译）。** 预编译能缓解启动成本，但为一个深度为 1 的
对象图引入第三方依赖与其升级负担，收益为负。

## 后果

- 启动路径保持线性：`App` 构造 → 关 IME → `MainWindow` → 视图模型 → `Loaded`
- 新增服务时**先问是否真的需要**；若对象图开始变深（≥3 层或多实现切换），
  重新评估本 ADR，而不是就地堆 `new`
- 不做 `interface` + 实现分离的纯仪式性抽象：没有第二个实现时直接用具象类
