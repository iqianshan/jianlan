# AC-08 可访问性验收记录

> 对应 `docs/requirements.md` §12 AC-08：**全流程可仅用键盘完成；焦点可见；屏幕阅读器可读出主要控件。**
> 对应 FR-10.7。本文只回答"能不能用键盘/读屏把活干完"，不重复 FR-10.7 的实现口径（见 `m2-plan.md` §4.10）。

## 1. 结论

**三项待验收全部闭合，走查过程中修掉 3 处真实缺陷。**

| 待验收项 | 结论 | 证据 |
|---|---|---|
| 焦点框的像素级确认 | **通过** | §3：真按键后焦点环确实被画出来，程序化聚焦时不画；环为 2px 实心描边，深色主题 5.38:1、浅色 4.56:1 |
| 高对比度实测 | **通过（修复一处后）** | §4：HC 主题 43 个键全走 `SystemColors`、0 处硬编码；修复"类型/大小"列 2.92:1 → 16.29:1 |

修复清单（均已含在本轮提交）：

2. `TabStrip.xaml` 的「+」按钮补 `AutomationProperties.Name`，绑到 ToolTip 同源文案。
3. `Theme.HighContrast.xaml` 的 `Brush.Text.Tertiary` 由 `GrayText` 改为 `WindowText`。

## 2. 方法：把"离屏做不了"变成"离屏能做"

`m2-plan.md` §4.10 第 5 条曾判定这件事做不了：WPF 只在真按过键之后才画焦点视觉，
`KeyboardNavigation.ShowKeyboardCues` 是 internal，离屏进程置不上。本轮把这条判定推翻了，
`tools/offscreen` 新增四个开关（均为走查工具，不进产品代码）：

| 开关 | 作用 |
|---|---|
| `--post-key <tab\|enter\|space\|left\|right\|…>[,..]` | 向**真实窗口句柄** `PostMessage(WM_KEYDOWN/WM_KEYUP)`，走 WPF 自己的消息处理链 |
| `--focus-stop <n>` | 把焦点停在 Tab 链第 n 个停靠点（走 `MoveFocus`，与真实 Tab 同序） |
| `--cues-shot <png>` | 先拍一张、翻键盘线索状态再拍一张，用两张图的像素差证明焦点视觉"平时不画、键盘来了才画" |
| `--active-tab <n>` / `--extra-tab <path>` | 把活动标签与标签数钉死，消除"上一次走查结果变成下一次起点"的污染 |

三条踩坑记录，避免后来的人重走：

- **`WM_UPDATEUISTATE` 这条路走不通。** 按系统惯例给窗口发 `UIS_CLEAR|UISF_HIDEFOCUS`，
  期望 WPF 翻转内部状态——实测两张图逐像素相同，说明 `HwndSource` 并不处理这条消息。
- **直接反射设那个 internal attached DP 也不够。** 设完 `GetValue` 读到 `True`，
  AdornerLayer 也在（`layer=ok`），但 `GetAdorners()` 为空：焦点视觉是挂在**焦点变化那一刻**的，
  已经聚焦的元素不会因为状态翻转自己补一圈。必须"先翻状态、再让焦点重走一遍"。
- **最终可靠的路径是投递按键。** `WM_KEYDOWN` 进 `HwndSource` 后由 WPF 正常翻译成按键路由事件，
  Tab 能移动焦点、Space 能切标签，全都按真实按键的行为发生。这也顺带证明了按键绑定真的接上了，
  而不只是"属性挂对了"。

## 3. 焦点框的像素级确认

同一停靠点（工具栏「刷新（F5）」按钮）、同一份二进制，两种聚焦方式各拍一张：

| 聚焦方式 | 焦点环 | 差异像素 |
|---|---|---|
| `Keyboard.Focus`（程序化） | **不画** | — |
| 投递 `WM_KEYDOWN`（Tab 走到） | **画出** | 55×55 区域内 615 px |

环的形状由逐行/逐列统计确认是描边而不是整块填充：
`rows = [49,52,53,10,8, …, 6(mid), …, 8,10,53,53,49]`，四边高、中间只剩 6 px（字形边缘）。

| 主题 | 焦点色 | 相邻背景 | 对比度 |
|---|---|---|---|
| 深色 | `#82A7FF` | `#1A1A1C` / `#202023` | **7.38 : 1** / 6.90 : 1 |
| 浅色 | `#245EEB` | `#F7F7F9` / `#FFFFFF` | **5.06 : 1** / 5.42 : 1 |

均高于 WCAG 1.4.11 对非文本对比度的 3:1 要求。（2026-11-14 强调色对齐 Logo 后重算，
两档都比原来更高；焦点环的**像素**实测仍是上面的 615 px，换色不改几何。）

**标签的焦点环是自绘的**（`Border` 用不了 `FocusVisualStyle`），同样做了像素对照：
有焦点时标签内出现一圈蓝色圆角描边（标签条区域 679 px 变化），无焦点时只有活动标签的下划线。
高对比度下这圈环取 `Highlight` 色，实测 11.17:1（§4）。

## 4. 高对比度实测

| 项 | 做法 |
|---|---|
| 开关 | `SystemParametersInfo(SPI_SETHIGHCONTRAST)`，flags `0x7E → 0x7F → 0x7E`（`finally` 里无条件恢复，实测已复原） |
| 方案 | 系统默认 `High Contrast Black` |
| 主题选择 | 不动设置：`ThemeService` 检测到 `SystemParameters.HighContrast` 后强制 `HighContrast`，忽略用户设置 |
| 取证 | 主窗口 / 标签栏（含焦点）/ 设置页各一张，均为 Release 产物 |

**静态核对（可重复，不依赖系统开关）：**

| 检查 | 结果 |
|---|---|
| HC 主题硬编码颜色 | **0 处** |
| HC 主题 `SystemColors` 引用 | **43 处**（43 个键全部指向系统色） |
| HC 与浅色主题的资源键差异 | **0**（界面引用的 65 个 `DynamicResource` 键，HC 一个都不缺） |

**动态核对（量像素，不靠眼睛）：**

| 位置 | 修复前 | 修复后 |
|---|---|---|
| 「类型」「大小」「修改日期」列的值 | `GrayText` `#686868` → **2.92 : 1** | `WindowText` `#FFFFFF` → **16.29 : 1** |
| 侧栏分区标题 / 空态提示 | 16.29 : 1 | 16.29 : 1 |
| 状态栏次要文字 | 6.69 : 1 | 6.69 : 1 |
| 标签焦点环 | — | 11.17 : 1 |

修复依据：这三列是**有效信息**，不是禁用态，2.92:1 在黑底上基本读不出来。
高对比度用户要的就是最高对比，层级让位于可读性——`Brush.Text.Disabled` 仍保留 `GrayText`，那是唯一该弱的。

> 残余的 `#686868` 像素未清空是抗锯齿边缘（白字压黑底的低覆盖度像素），逐块放大后文字主体均为白色。

## 5. 标签的真实按键走查

起点固定（`--active-tab` + `--extra-tab` 造两个可区分标签），每项都读活动标签序号：

| 按键 | 起点 | 结果 | 判定 |
|---|---|---|---|
| `Space` | 活动=1，焦点在第 1 个标签 | `1 → 0` | ✅ |
| `→` | 活动=0，焦点在第 1 个标签 | `0 → 1` | ✅ |
| `←` | 活动=1，焦点在第 2 个标签 | `1 → 0` | ✅ |
| `Enter` | 活动=1，焦点在第 1 个标签 | `1 → 1`（**不动**） | ❌ → 修复后 `1 → 0` ✅ |

**根因**：`KeyBindings` 里 `Enter`（无修饰键）绑的是 `OpenItem`，窗口的 `PreviewKeyDown`
先于元素的 `KeyDown` 执行，于是 `e.Handled = true` 并派发"打开选中项"——焦点在标签上按 Enter，
打开的是旁边列表里的文件，标签纹丝不动。`Space` 之所以正常，恰恰因为它不在键位表里。

**修复**：在 `OnPreviewKeyDown` 里加一条让路规则——无修饰键的 `Enter/Space/←/→` 且焦点元素
`DataContext` 是 `TabViewModel` 时直接返回。范围刻意收窄到四个键，`Ctrl+W`、`F5`、`Ctrl+Tab`
这些全局键位在标签上仍然生效。

这条路也说明一件事：**只走代码路径的走查会漏掉它**。`TabStrip.OnTabKeyDown` 的 switch 写得很完整，
单测与代码阅读都挑不出毛病，问题出在它上游的窗口级拦截。

## 6. 屏幕阅读器可读性

以 Tab 链上的 20 个停靠点为样本，读 `AutomationProperties.Name`：

| 类别 | 数量 | 说明 |
|---|---|---|
| 显式名称 | 14 | 标签、导航行、分隔条、设置、上级、刷新、搜索、视图切换、分屏 |
| 靠内容作名称 | 4 | 列头按钮（「名称 ▲」等），内容本身可读 |
| 靠内容作名称 | 2 | 面包屑（「D:」「ac05」），内容本身可读 |
| **无名** | 1 | 「+」新建标签按钮——纯图标，内容是一个私用区字形 |

修复：`AutomationProperties.Name="{Binding ToolTip, RelativeSource={RelativeSource Self}}"`，
与可见提示同源（禁用时自动读「已达上限」），修复后读作「新建标签页（Ctrl+T）」。

**2026-11-26 补测（侧栏整表）**：用 `tools/window-drive/uia_nav_dump.ps1` 把侧栏每一行
的可访问名整批读出来，不再只抽 Tab 链上的停靠点。结果发现一类此前没测到的缺陷：

| 行类型 | 改前读作 | 改后 |
|---|---|---|
| 分区标题（位置 / 收藏 / 标签 / 工作区 / 历史） | `Jianlan.App.ViewModels.NavSectionRow` | 位置 / 收藏 / 标签 / 工作区 / 历史 |
| 「此电脑」行 | `Jianlan.App.ViewModels.NavThisPcRow` | 此电脑 |
| 空态提示行 | `Jianlan.App.ViewModels.NavEmptyRow` | 在目录里按 Ctrl+D 收藏当前位置（等原文） |

原因是 `ListBoxItem` 的可访问名取数据对象的 `ToString()`，而这些行类型没覆盖它，
默认实现就是类型全名。屏读器会逐个字母念出 `Jianlan.App.ViewModels...`。

修法：`NavRow` 上加 `virtual string AccessibleName`，各子类覆盖成界面上那行字，
基类 `override ToString()` 返回它。`NavItem`（位置项）是 record，本来就有可读的
`ToString()`，不受影响——所以这十行里只有「桌面/文档/下载」一直是正常的，
更不容易被发现。

这也说明"只抽 20 个停靠点读名称"不够：被抽到的恰好都是有名称的那几类。
